2026-11-01 · 노진산

## 1. venues와 rooms를 합칠지

합치는 게 맞습니다. 호실을 나눈 이유는 '한 스터디카페 안의 101호·201호'였는데, 공간대여에서는 크롤링한 공간 하나를 우리 공간 하나로 등록하기로 했으니(10/30 회의) 지점이 늘 룸 하나뿐입니다. 표를 나눠 두면 조인만 늘고 얻는 게 없습니다.

| | 지금 (venues + rooms) | 제안 (rooms 하나) |
| --- | --- | --- |
| 표 | venues(지역·이름·소개·홍보·영업시간·출처) + rooms(유형·인원·가격·최소 시간) | rooms에 모두 |
| 검색 | rooms ⋈ venues ⋈ regions | rooms ⋈ regions |
| 크롤러 적재 | 두 표에 나눠 넣고 FK 연결 | 한 줄 upsert, `UNIQUE (source_site, source_id)`도 rooms로 |
| 화면 표기 | '관악 스터디하우스 · 201호 그룹룸' | '신촌 스터디룸 2호' 같은 이름 하나 |
| 잃는 것 | — | '같은 업체의 여러 방' 표현. 필요해지면 그때 `host_id`를 더하면 됨 |

- 표 이름을 `rooms`로 두면 `reservations.room_id`, `reservation_slots` 기본키, 뷰 `v_room_rating`, API `/rooms/...`, 프론트가 그대로입니다. 바뀌는 건 venues의 컬럼(`region_id`, `promo_text`, `open_hour`, `close_hour`, `new_until`, `source_site`, `source_id`)이 rooms로 옮겨 오는 것뿐입니다.
- 공간 하나에 유형 하나(`category_id`)입니다. 스페이스클라우드는 한 공간에 유형이 여러 개 붙어 있으므로(예: 회의실·세미나실), 적재할 때 우리 5개 유형 중 하나로 정하는 규칙이 필요합니다(아래 3-2-2).
- 고칠 곳: `공간대여_02`(표 16개 → 15개, ERD), `공간대여_03`(상세 응답에서 venue 묶음 제거), 프론트 목업의 `venue`·`room` 두 칸 → `name` 한 칸. 프론트 수정은 반나절 안쪽입니다.

## 2. 가상 날짜

### 2-1. 어디에 둘지 — DB

가상 날짜는 DB에 한 줄로 두고, 두 서버가 같은 값을 읽게 합니다.

| | `.env` | DB `sim_clock` (제안) |
| --- | --- | --- |
| 바꾸는 법 | 서버 두 대의 `.env`를 고치고 둘 다 재시작 | `PUT /internal/clock` 한 번(또는 스크립트) |
| 서버 둘이 어긋날 때 | 한 대만 고치면 A는 11/8, B는 11/1로 '오늘'이 달라 14일 창·NEW 배지·후기 자격이 서로 다르게 판단됨 | 같은 줄을 읽으므로 어긋나지 않음 |
| 재시작 | 필요(진행 중 요청 끊김) | 필요 없음 |
| 기록 | 남지 않음 | `updated_at`, 바꾼 사람·이유를 남길 수 있음 |

```sql
CREATE TABLE sim_clock (
  id         TINYINT PRIMARY KEY DEFAULT 1,   -- 늘 한 줄
  sim_date   DATE NOT NULL,                   -- 가상 '오늘'
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  CHECK (id = 1)
);
```

- 백엔드 공통 함수 `get_sim_today(db)` 하나로만 읽습니다(A의 `core/`에 두고 B도 씀 → 새 '약속'). 매 요청 DB를 읽기 부담되면 10초 캐시.
- 바꾸기: `PUT /internal/clock {sim_date}` 또는 `POST /internal/clock/advance {days: 7}`. `/internal/*`는 이미 Nginx에서 외부 차단하기로 한 경로라 그대로 씁니다. 날짜를 되돌리는 것은 막습니다(예약·후기가 꼬임).
- 프론트도 '오늘'을 알아야 하므로 공개 `GET /clock` → `{sim_date, server_time}`. 지금 프론트는 브라우저 날짜를 쓰니, 이 API가 생기면 `utils/date.js`의 `todayISO()`만 바꾸면 됩니다.
- 오프라인 대량 생성기(1년치 백필)는 서버를 거치지 않고 자기 가상 시계로 DB에 바로 씁니다. `sim_clock`은 화면 시연과 Locust처럼 **서버를 거치는 흐름**용입니다.

### 2-2. 가상 날짜와 실제 시각을 어디에 쓸지

원칙은 **'오늘이 며칠인가'는 가상, '몇 분 지났나'는 실제**입니다. 가상 '지금' = 가상 날짜 + 실제 시각(시·분)으로 봅니다.

| 쓰는 곳 | 기준 | 이유 |
| --- | --- | --- |
| 예약 가능 범위(오늘부터 14일), 지난 칸 막기 | 가상 날짜 + 실제 시각 | 예약 규칙의 '오늘' |
| `reservations.reserve_date`, `reservation_slots.slot_date` | 가상 | 이용일 자체 |
| 결제 대기 10분(`expires_at`) | **실제** | 사람이 실제로 결제하는 시간. 가상으로 하면 날짜를 넘기는 순간 대기 건이 한꺼번에 풀림 |
| 이용 완료 전환, 후기 작성 기간 | 가상 날짜 | 2-3 |
| NEW 배지(`new_until`), 신규 공간 등록 주기 | 가상 날짜 | '7일마다 새 공간'이 가상 주 기준 |
| 로그인 토큰 만료, 요청 제한, 크롤러 요청 간격 | 실제 | 보안·예의는 실제 시간 |
| `created_at`·`updated_at`, 서버 로그 | 실제 | 장애·감사 추적 |
| 활동 로그 `user_events` | **둘 다**: `occurred_at`(실제) + `sim_date`(가상) | 분석은 가상 날짜로, 디버깅은 실제 시각으로 |
| 예약을 한 날 | 둘 다: `created_at`(실제) + `booked_sim_date`(가상) | '며칠 전에 예약하나'(리드타임) 분석에 가상 날짜가 필요 |

- 표에 컬럼 두 개(`user_events.sim_date`, `reservations.booked_sim_date`)를 더합니다.
- 통계·분석 쿼리는 언제나 가상 날짜 컬럼으로 묶습니다. 실제 시각으로 묶으면 하루에 가상 4주가 지나간 날이 이상치가 됩니다.

### 2-3. 이용 완료와 후기 작성 시점

팀원 제안대로 **이용일 다음(가상) 날부터**가 좋습니다. 가상 시각(시·분)까지 맞출 필요가 없어집니다.

- `confirmed` → `completed`: `reserve_date < 가상 오늘`인 것. 지금 설계는 '1시간마다 이용 종료 시각 확인'인데, 가상 날짜를 한 번에 7일 넘기면 시각 비교가 의미가 없으므로 **날짜를 넘길 때 + 하루 한 번** 돌리는 것으로 바꿉니다(`jobs/complete_reservations.py`).
- 후기: `completed`이고 `가상 오늘 ≤ reserve_date + 7`일 때 작성 가능(기존 '이용 후 7일 안' 유지).
- 프론트 목업은 이미 '날짜가 지난 확정 예약 = 이용 완료'로 처리하고 있어 바꿀 것이 없습니다.

## 3. 크롤링

### 3-1. 실제 정보를 써도 되나, 가상 데이터로 대신할까

둘을 섞는 것을 제안합니다. **실제 사이트에서는 분포(가격대·인원·시설·지역)만 가져오고, 화면에 보이는 정체성(이름·소개·홍보 문구·사진)은 우리가 만듭니다.**

| | 크롤링 그대로 | 가상만 | 섞기 (제안) |
| --- | --- | --- | --- |
| 가격·인원·시설의 현실성 | 높음 | 우리가 정한 규칙 그대로 | 높음 |
| 법·윤리 위험 | 실제 업체 이름·소개를 우리 공간처럼 보여주게 됨 | 없음 | 낮음(속성 숫자만) |
| 배치 파이프라인 경험(수집→변환→적재) | 있음 | 없음 | 있음 |
| 외부 사이트에 기대는 정도 | 사이트가 바뀌면 멈춤 | 없음 | 크롤링이 비면 가상 풀로 채워 등록이 멈추지 않음 |

- 실제 업체 이름·소개 문구를 우리 서비스의 예약 가능한 공간처럼 보여주면, 그 업체가 우리 서비스에 입점한 것처럼 보입니다. 소개 문구는 호스트가 쓴 글이라 저작권도 있습니다. 수업용이어도 피하는 게 맞습니다.
- 그래서 이름은 `지역 + 유형 + 번호`(예: '신촌 스터디룸 3호'), 소개·홍보 문구는 유형별 템플릿 몇 개를 돌려 씁니다. 출처 id는 내부 컬럼에만 남깁니다.
- 실제로 크롤링 자체가 괜찮은지는 강사님 질문 목록(10/30 회의 문서)에 이미 있습니다. 답이 '하지 마라'면 같은 구조에서 크롤러만 빼고 가상 풀로 돌리면 됩니다.

### 3-2-1. 어느 사이트

스페이스클라우드 한 곳으로 시작합니다. 사이트맵에 공간 14,137개가 있고 robots.txt가 상세(`/space/<id>`)를 허용합니다. 쉐어잇은 2단계, 아워플레이스·네이버 예약은 robots.txt가 전부 막아 제외입니다(10/30 회의 문서).

유형 대응은 `공간대여_01_기능정의.md`의 '유형 정의와 크롤링 매핑' 표를 따릅니다(스터디룸 = 스터디룸·회의실·세미나실·강의실). 그 기준으로 200개 표본에서 걸리는 비율이 크게 다릅니다.

| 우리 유형 | 스페이스클라우드 유형 (01 문서) | 표본 200개 중 | 상세 20건에서 1개 이상 나올 확률 |
| --- | --- | --- | --- |
| 파티룸 | 파티룸, 공유주방 | 66 이상 | 거의 100% |
| 스튜디오 | 촬영·렌탈스튜디오, 호리존, 실외촬영, 녹음실, 라이브방송 | 35 | 약 98% |
| 스터디룸 | 스터디룸, 회의실, 세미나실, 강의실 | 29 (그중 10명 이하 11) | 약 96% (10명 이하만이면 약 68%) |
| 카페 | 카페 | 9 | 약 60% |
| 영화관 | 대응 유형 없음 | 0 | 0% → **가상으로만** |

- 확률은 표본 비율 p로 `1 − (1 − p)^20`을 계산한 값입니다. 공간 하나에 유형이 여러 개라 행끼리 겹칩니다.
- 카페는 한 번에 못 찾을 때가 많고, 스터디룸도 인원 제한을 걸면 비슷해집니다. 그래서 아래 3-2-4의 후보 풀이 필요합니다.

### 3-2-2. 수집 항목

DB에 이름·소개·홍보 문구 칸이 있지만, 이 칸은 크롤링 값이 아니라 생성 값으로 채웁니다. 지금 크롤러는 업체 이름(`name`)을 저장하고 있어서, 적재 단계에서 쓰지 않거나 수집에서 빼야 합니다.

| 수집 | 우리 표에서 | 비고 |
| --- | --- | --- |
| `source_site`, `source_id`(URL 뒤 번호) | rooms | 중복 등록 막기(UNIQUE) |
| 공간유형 목록 | `category_id` | 위 표 기준으로 5개 중 하나. 여러 개면 01 문서대로 목록의 첫 유형 |
| 주소의 시·도 + 시·군·구까지 | `region_id` | 동·번지 이하는 저장 안 함 |
| 최소·최대 인원 | `capacity_min/max` | 이미지 풀 고를 때도 씀 |
| 시간당 가격(세부 공간 중 최저), 최소 예약 시간 | `price_per_hour`, `min_hours` | 1인당 가격이면 × 최소 인원 |
| 영업시간 | `open_hour`, `close_hour` | 24시간이면 9~23으로 자름(우리 칸은 9~22시) |
| 시설 아이콘 이름 | `room_facilities` | 3-2-3 |
| 수집 시각 | `crawl_jobs` | |
| **수집하지 않거나 쓰지 않음** | — | 업체 이름, 소개·홍보 글, 사진, 후기 본문·작성자, 호스트·연락처, 상세 주소 |

### 3-2-3. 시설

랜덤 대신 크롤링한 시설을 씁니다. 지금 크롤러가 상세 페이지에서 시설 아이콘을 이미 뽑고 있어(`인터넷/WIFI`, `TV/프로젝터`, `의자/테이블` 등) 추가 요청이 없습니다. 우리 `facilities` 목록에 맞춰 이름을 바꾸는 표 하나만 만들면 됩니다(예: `TV/프로젝터` → 빔프로젝터, `인터넷/WIFI` → 와이파이). 목록에 없는 시설은 버리고, 시설이 하나도 없거나 가상 풀에서 만든 공간(영화관 등)만 유형별 확률로 랜덤 지정합니다. 그래야 '시설 필터로 검색 → 예약'의 분석이 실제 분포를 따릅니다.

### 3-2-4. 주기와 개수

가상 날짜는 하루에 몇 주씩 넘길 수 있지만 크롤링은 실제 시간으로 천천히 해야 하므로, **수집과 등록을 나눕니다.**

1. **수집 (실제 주 1회):** 사이트맵에서 새 id를 찾고 상세를 최대 20건 열어(3초 간격, 약 1분) 조건에 맞는 것을 후보 풀(`crawl_candidates` 또는 `crawl_jobs` 결과)에 쌓습니다. 처음 한 번은 기준선으로 후보를 넉넉히 모읍니다(상세 20건 초과는 `crawler/AGENTS.md`에 따라 사람 승인).
2. **등록 (가상 주마다):** 가상 날짜가 7일 넘어갈 때 후보 풀에서 유형별로 1개씩 꺼내 등록합니다 → **주 +5개**, NEW 배지 14일. 풀에 그 유형이 없으면(영화관은 늘) 가상 풀에서 만듭니다.
3. **상한:** MVP는 시작 10개(지금 화면 목업과 같은 수) → 4주 뒤 30개 안팎에서 멈추고, 동시성·분석 기준을 통과하면 늘립니다(`MVP_시뮬레이션_크롤링_수치.md`의 단계 조건).

| 가상 주차 | 공간 수 | 하루 칸(×14) | 가상 사용자 풀(하루 칸 × 2.5) |
| --- | --- | --- | --- |
| 0 (시작) | 10 | 140 | 350 |
| 1 | 15 | 210 | 525 |
| 2 | 20 | 280 | 700 |
| 3 | 25 | 350 | 875 |
| 4 | 30 | 420 | 1,050 |

공간이 늘 때 사용자 풀도 같이 늘려 '하루 방문 = 하루 칸 수' 규칙(점유율 약 60%)을 지킵니다. 주 +5가 많으면 +2(번갈아 유형)로 줄여도 구조는 같습니다.
