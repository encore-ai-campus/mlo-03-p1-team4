# 이슈 #17: 109 서버 재시험 실행표

작성: 2026-11-08. 이 문서는 사전 준비다. 109 서버 접속·배포·재시험 결과를 이미 확인했다는 뜻이 아니다. PM의 팀 공유 시험 보고서와 PR #97을 현재 계획의 기준으로 삼는다.

접속 정보·암호·합성 키는 작업판이나 측정 문서에 붙이지 않는다. 실제 배포와 VM 설정 변경은 서버 담당자가 잠금 소유권을 확인한 뒤 수행한다. 개인 비공유 환경 결과는 팀의 공식 검증 근거로 사용하지 않는다.

## 실행 순서

1. 새 `run_id`와 배포 지문·설정·시각·시험자·측정 파일 위치를 기록한다. 이전 실행과 숫자를 합치지 않는다.
2. API 응답·파일·MongoDB·예약 이벤트를 한 건씩 대사하는 smoke를 통과시킨다. 이어 5·20·50 VU에서 같은 대사를 확인한다. 어느 단계에서 오류나 차이가 나면 증량하지 않는다.
3. 저부하 대사가 모두 통과한 경우에만 100→200→400 VU 쓰기 회귀를 진행한다. 실제 참여 인원을 별도로 기록한다. 목표 인원 미달은 해당 단계 통과가 아니다.
4. 단계마다 전체 HTTP RPS·p95/p99, 예약 POST 전체 p95/p99, 새 예약 201 수·기존 예약 재응답 200 수, 취소·환불 성공과 5xx·전송 실패를 분리한다. 200을 신규 예약 처리량에 넣지 않는다.
5. 전후 api1·api2 각각의 파일 실패 stage/reason 카운터, 잠금 대기·전체 파일 기록 시간 histogram, MongoDB 실패 카운터와 안전 필드 앱 로그를 확인한다. 프로세스 재시작 시 카운터가 초기화될 수 있으므로 워커 시작 시각도 남긴다.
6. 이번 실행의 고유 `event_id`를 발송 기록·`events.log`·MongoDB에서 대조한다. 예약 생성·취소 유형별 총수만으로 누락 0을 판정하지 않는다. 재적재가 필요하면 대상 로그 범위를 확정하고 고유 인덱스·중복 방지를 확인한 뒤 실행한다.
7. DB 담당과 예약·결제 1:1, 취소·환불, 잔여 슬롯 및 primary/replica 정합성을 확인한다. PM·B는 워밍업 실패 후 예약 재시도 200의 원인과 실제 VU를 해석한다.

## 결과 판정과 중단 조건

- 파일 기록 실패 증가량 **0건**. 파일에 없는 이벤트는 MongoDB 재적재로 되살릴 수 없다.
- 로그를 기준으로 MongoDB 고유 ID 누락·중복 **0건**(필요 시 범위를 제한해 재적재한 뒤). 발송 측 고유 ID 수와 로그 고유 ID 수도 대조한다. 생성기가 MongoDB에 직접 넣은 과거 데이터는 제외한다.
- 예약 생성·취소·결제 결과가 맞고 MongoDB 장애가 있어도 예약 API 성공이 유지되는지는 팀이 승인한 공유 시험 환경에서 확인한다.
- 예약 p95·오류는 동일 조건의 PM 이전 값과 비교한다. 변경한 실패 처리·대체 기록 경로가 예약 응답과 이벤트 정합성에 미친 영향을 함께 확인한다. 기준 미달·원인 미확정이면 수치와 한계를 기록하고 완료 처리하지 않는다.
- 준비·예열 오류, 실제 VU 미달, 배포·실행기·설정의 미기록 변경, 지표 누락 중 하나라도 있으면 그 단계는 **미검증**으로 표시하고 증량을 멈춘다.
