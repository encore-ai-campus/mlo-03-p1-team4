# F-60 · API 이벤트 재전송 계약 제안 (2026-11-07)

상태: **후속 이슈 제안, 미구현**. PM은 11-07 #17에서 로그 재적재 중복만 측정하고 API 재전송 방지는 별도 이슈로 분리하기로 결정했다. 이 문서는 그 후속 작업의 선택지를 정리한다. 기준 문서는 `docs/백엔드_A_회원_후기_이벤트.md`와 `docs/산출물_05_구현_운영_계획.md`다.

## 사용자에게 생기는 일

브라우저가 이벤트를 보냈지만 응답을 받지 못하면 같은 이벤트를 다시 보낼 수 있다. 현재 FE는 이벤트마다 UUID를 만들지만, A는 요청의 `event_id`를 저장에 사용하지 않고 매번 새 UUID를 발급한다. 같은 요청을 두 번 보낸 로컬 시험에서 HTTP 202 두 번, `events.log` 두 줄, MongoDB 두 문서가 나왔다. 사용자 행동 한 번이 분석에서는 두 번으로 보일 수 있다. FE의 현재 `flush()`는 실패한 묶음을 큐에 되돌리지 않아, 반대로 전송 전에 잃을 수도 있다.

## 선택지와 판단

| 선택지 | 얻는 것 | 비용·한계 | 판단 |
| --- | --- | --- | --- |
| A. 현재처럼 서버가 매 요청 새 ID 발급 | 기존 구현 유지 | 같은 요청의 재전송을 구별할 수 없음 | 권장하지 않음 |
| B. 클라이언트 ID가 있으면 보존, 없으면 서버가 발급 | FE의 기존 UUID를 재전송마다 유지할 수 있고, 기존 ID 없는 호출도 계속 허용 | 같은 ID의 로그 줄은 여러 개일 수 있어 원시 줄 수 대신 고유 ID로 측정해야 함 | **권장** |
| C. 서버가 응답에서 ID를 발급 | 서버가 ID를 통제 | 첫 응답이 유실되면 클라이언트가 ID를 몰라 안전하게 재시도할 수 없음 | 권장하지 않음 |

## 권장 계약

1. FE 이벤트의 `event_id`는 현재 요청 스키마대로 선택 사항을 유지한다. 제공된 UUID는 A가 `events.log`와 MongoDB에 그대로 쓴다. 없으면 A가 UUID를 만든다. B 서버 이벤트는 계속 서버가 UUID를 만든다.
2. 같은 클라이언트 이벤트를 재시도할 때 FE는 같은 `event_id`를 유지한다. 새 행동에는 새 UUID를 쓴다. FE의 실패 큐는 응답을 확인할 때까지 보존하고, 202를 받은 묶음만 제거한다. 이 FE 수정은 FE 담당 범위다.
3. API의 `accepted`는 유효한 요청 이벤트 수로 유지한다. MongoDB 고유 저장 수와 다를 수 있으므로, #17은 **전송 시도 수**, **고유 클라이언트 ID 수**, **로그 고유 ID 수**, **MongoDB 고유 ID 수**를 분리해 기록한다. 같은 ID의 로그 줄 재전송과 replay는 MongoDB 고유 인덱스가 한 문서로 수렴시킨다.
4. A 구현은 `ClientEventContext`에 선택적 ID를 전달하고 `_log_event()`에서 그 ID를 우선 사용하면 된다. 공개 `log_event(...)`의 이름·인자·반환값과 `/events` 응답 형태는 유지한다. 현재 “재전송마다 새 ID”를 기대하는 A 테스트는 권장 계약이 확정된 뒤 바꾼다.

## 결정과 검증 항목

- 후속 이슈의 PM·FE·A: 선택지 B와 `accepted` 의미, FE 실패 큐 재시도 범위를 확정한다. 이번 #17의 중복률 0%는 로그 재적재만 뜻한다.
- A: ID가 있는 요청 두 번 → 로그에는 같은 ID 두 줄, MongoDB에는 한 문서; ID 없는 레거시 요청 → 서버 ID 발급; 서로 다른 두 ID → 두 문서; 파일 실패는 503, MongoDB 실패는 202와 replay 가능을 확인한다.
- FE: 실패·온라인 복귀·페이지 종료 재시도에서 같은 ID를 유지하고, 성공한 묶음만 큐에서 제거한다.
- 최종 측정: 재전송을 제외한 고유 이벤트 수를 유실률 분모로 쓰고, 재전송 시도 횟수는 별도 보고한다. 직접 적재된 생성기 이벤트는 제외한다.

이 제안은 B의 예약 API·예약 이벤트 계약, DB 스키마, 공개 `log_event` 함수 서명을 바꾸지 않는다. API 재전송 코드는 이번 #17에서 변경하지 않았다.
