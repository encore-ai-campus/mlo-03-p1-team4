# 가상 날짜 제안 검토와 결정

2026-11-03 · 대상: 팀원 제안 [「가상 날짜 도입 시 담당별 고려사항」](제안_2026-11-03_가상날짜_담당별고려사항.md)(원문 그대로 보관) · 결정: **실제 날짜, 가상 날짜 없음, 예약 날짜는 과거·미래 모두 열기**

## 1. 제안 요약

- 가상 날짜 하나를 DB에 저장하고 API로 하루씩 옮긴다. 시각은 실제 시각 그대로.
- 예약 가능 기간·NEW·인기순·이용 완료는 가상 날짜로 판단한다.
- 활동 로그에는 실제 시각과 그때의 가상 날짜를 함께 남긴다.
- 날짜를 옮길 때 지난 예약을 완료 처리하고, 신규 공간 공개 시점도 가상 날짜에 맞춘다.

제안이 풀려는 문제: **실제 날짜로는 예약이 '이용 완료'가 되기까지 하루를 기다려야 해서, 완료·후기 흐름과 날짜별 데이터를 시연 기간에 보기 어렵다.**

## 2. 검토

| 관점 | 가상 날짜 | 실제 날짜 + 지난 날짜 예약 허용 (채택) |
| --- | --- | --- |
| 완료·후기 시연 | 날짜를 넘기면 됨 | 지난 시간으로 예약하면 만들 때 바로 `completed` → 바로 후기 |
| 날짜별 데이터 양 | 날짜를 넘기며 쌓음(사람이 계속 조작) | 생성기가 과거 기간을 한 번에 백필 + 사용자 예약 |
| 바뀌는 곳 | 새 표 1개, 날짜 이동 API, 모든 날짜 판단, 이벤트·예약에 칸 추가, 프론트 오늘 기준 | 검증 범위 한 줄, 완료 조건 한 줄, 후기 기한 한 줄 |
| 서버 2대 일관성 | 가상 날짜를 매 요청 DB에서 읽거나 캐시 무효화 필요(서버마다 다른 날짜면 버그) | 두 서버가 같은 실제 시계 |
| 시각과 날짜 섞임 | '가상 11월 14일인데 실제 시각 11월 3일 14시' 같은 조합을 모든 쿼리가 다뤄야 함(인기순·NEW·취소 기한) | 하나의 시계 |
| 관측(Loki·Prometheus) | 실제 시각으로 찍혀 대시보드와 가상 날짜가 어긋남 | 그대로 맞음 |
| 1차 일정(3일) | 무거움 | 가벼움 |

남는 비용과 대응:

- 지난 날짜 예약은 실제 수요가 아니어서 분석을 흐린다 → `reserve_date < DATE(created_at)`로 따로 본다(`산출물_04` 8절). 표에 칸을 더하지 않는다.
- 취소 기한은 실제 시각 기준이라 지난 예약은 취소할 수 없다 → 의도한 동작(`NOT_CANCELLABLE`).
- 후기 기한이 '이용일 + 7일'이면 오래된 날짜로 예약했을 때 바로 막힌다 → 기한을 `max(이용일, 예약한 날) + 7일`로 바꿈.
- 테스트에서 날짜를 고정해야 할 때는 `TODAY_OVERRIDE`(테스트 전용)를 쓴다. 운영 기능이 아니다.

## 3. 결정과 반영

| 항목 | 정한 것 | 반영한 곳 |
| --- | --- | --- |
| 날짜 | 실제 날짜, 가상 날짜·날짜 이동 API·가상 날짜 표 없음 | `산출물_01` F-63·3절, `AGENTS.md` |
| 예약 범위 | 오늘 기준 과거 `BOOKING_PAST_DAYS`·미래 `BOOKING_FUTURE_DAYS`(기본 각 365일), 지난 시간도 가능 | `백엔드_B` 5-2·6절, `backend/.env.example` |
| 이용 완료 | 끝나는 시각이 지났으면 만들 때 바로 `completed`, 나머지는 1시간 배치 | `산출물_01` F-35, `백엔드_B` 6절, `backend/app/jobs` |
| 후기 기한 | `max(이용일, 예약한 날)`부터 7일 | `백엔드_A` 5-2 |
| 칸 표시 | `past`는 표시용, 막지 않음 | `백엔드_B` 5-2, `프론트_변경목록_11-03.md` |
| 분석 | 지난 날짜 예약은 `reserve_date < DATE(created_at)`로 구분 | `산출물_04` 8절 |
| 데이터 양 | 생성기 과거 백필 + Locust | `simulator/` |

제안의 '신규 공간 공개 시점'은 실제 날짜로 정리된다: 크롤러가 넣은 날의 `created_at`부터 14일이 NEW.
