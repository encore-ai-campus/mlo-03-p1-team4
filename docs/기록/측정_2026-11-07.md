# F-60 · 이슈 #17 수집 신뢰성 측정 준비 (2026-11-07)

상태: **정상 수집·재적재 및 API 관점의 5분 MongoDB 연결 불가 시험 완료. PM이 공유한 400명 부하 중 파일 기록 실패 3건에 맞춰 잠금 대기와 계측을 보완했고 로컬 회귀 19건 통과. 같은 109 부하 재시험과 실제 MongoDB 서비스 중단·예약 영향은 미측정**. 기준은 `docs/산출물_05_구현_운영_계획.md` 5-2절이다.

## 범위와 숫자의 뜻

- API를 거친 이번 시험의 이벤트만 센다. 생성기가 MongoDB에 직접 쓴 과거 이벤트는 제외한다(#38 결정).
- 시험마다 고유한 `session_id`와 `user.session_sequence` 범위를 사용하고, 시작·종료 시각과 API 응답의 `accepted`·`ignored`를 기록한다. 실제 `events.log`와 MongoDB에서는 그 세션의 `event_id` 집합을 비교한다. 다른 사용자·시험의 이벤트를 합산하지 않는다.
- `보낸 수`는 프론트에서 만든 수와 API가 접수했다고 응답한 수를 따로 적는다. HTTP 202의 `accepted` 합계를 서버 접수 분모로 삼는다. 400·503·통신 실패, `ignored`는 별도 기록한다. 프론트 생성 수를 모르면 프론트→API 구간 유실률은 계산하지 않는다.
- 로그 누락은 재전송을 제외한 고유 사용자 이벤트 수와 로그 고유 ID 수를 비교해 판단한다. DB 누락은 로그 `event_id` 집합과 MongoDB `event_id` 집합의 차이로 확인한다. 최종 유실률은 고유 사용자 이벤트 수를 분모로 계산하고, API 접수 시도 수는 별도로 기록한다. 고유 사용자 이벤트 수를 모르면 유실률을 계산하지 않는다. 같은 ID의 로그 줄 중복과 MongoDB 중복 문서는 따로 센다.
- `events.log`에는 서버가 만든 `event_id`가 들어간다. 현재 API는 클라이언트가 보낸 `event_id`를 저장에 사용하지 않는다. PM의 11-07 결정에 따라 이번 #17의 중복률 0% 근거는 로그 재적재만 사용하며, API 요청 재전송은 알려진 제한으로 기록하고 후속 이슈에서 처리한다.
- PM이 109 테스트 서버의 400명 예약 부하 결과로 공유한 파일 기록 실패 3건(예약 이벤트 20,936건 중 3건, 약 0.014%)은 기존 지표에 별도 기입한다. 이번 브랜치에서는 파일 잠금 최대 대기를 0.1초에서 0.5초로 늘리고, `event_file_write_failures_total`을 추가해 같은 부하에서 재현 여부와 예약 응답 지연을 다시 확인한다. 해당 원본 로그를 이 PC에서 직접 검토하지 않았으므로 PM 제공 측정값으로 표시한다.

## 합격선과 남은 검증

- 기준 문서의 제안 합격선: 유실률 0.1% 미만, 대체 저장 뒤 유실 0%, MongoDB 문서 중복률 0%, 장애 중 예약 API 실패 0건. 수치가 없으면 `미측정`으로 둔다.
- PM 결정(#17 댓글, 11-07): 로그 재적재 중복만 이번 중복률 0%의 근거로 삼는다. API 요청 재전송의 초과 저장은 별도 지표이며 후속 이슈로 분리한다.
- 프론트 `useEventLogger.js`는 `flush()`에서 큐를 먼저 비우고 전송 실패를 잡아 종료한다. 현재 코드 기준으로 프론트 생성 수와 API 접수 수 사이의 손실 가능성이 있으므로, 이 구간을 별도 관찰한다. 프론트 변경은 FE 담당과 계약 결정이 필요하다.

## 시험 서버 재확인 (2026-11-07)

- MariaDB `100.100.100.31:3306`은 Linux MariaDB 10.11.14다. `spacecube_test`에 기준 12개 테이블과 1개 view가 있고, seed 기준 건수도 `categories=5`, `facilities=20`, `regions=230`으로 맞는다. 기존 행은 사용자 3명이며 공간·예약·시간 칸·결제·후기는 0건이다. DDL이나 seed는 다시 실행하지 않았다.
- 이 서버에는 `codex@100.100.100.1` 계정이 이미 있으나 CREATE/DROP 권한이 있어 #17 시험에는 사용하지 않는다. Workbench의 `runner@100.100.100.1` 전역 권한도 확인되어 회수했고, `SHOW GRANTS`에서 USAGE만 남은 것을 확인했다. `issue17_runner@100.100.100.1`는 당시 없었다. 이를 `spacecube_test`의 SELECT/INSERT/UPDATE/DELETE만 갖도록 준비하는 숨김 입력 스크립트를 추가했으며, 관리자 비밀번호·새 시험 비밀번호 입력 후 `APPLY` 제출을 기다린다. 비밀값은 GitHub나 문서에 옮기지 않는다.
- MongoDB `100.100.100.40:27017` 인증은 성공했고 서버는 8.0.34다. 전용 테스트 DB와 `events` 컬렉션은 이미 있고, `uq_event_id` 고유 인덱스와 TTL 인덱스 등이 있다. 확인 당시 `events` 문서는 24건이었으며 비합성 데이터도 포함되어 있어 기존 문서와 인덱스는 건드리지 않는다. 저장 비밀값은 기록하지 않는다. 시험 계정은 `shutdown` 권한이 있어 서비스 중단을 실행할 수 있지만, MariaDB 접속 대상이 확인되지 않아 아직 중단하지 않았다.
- MongoDB root 비밀번호가 채팅·문서·로그 등에 공유된 적이 있으면 새 값으로 교체한 뒤 시험 API와 재적재 스크립트에 숨김 입력합니다. `.31` 관리자 비밀번호도 같은 값이면 `.31`도 교체합니다.
- 현재 `127.0.0.1:8001` API가 `.31/.40`을 바라보는지는 확인되지 않았다. 읽기 전용 `GET /venues`가 공간 1건을 반환했지만 `.31/spacecube_test.venues`는 0건이고, 확인 가능한 프로젝트 `.env`는 MariaDB `.212`, MongoDB `.211`을 가리킨다. 따라서 이 API로 시험 이벤트나 예약 요청을 보내지 않았다.
- `.31/.40` 별도 시험 API 시작 및 복구 후 재적재·측정 스크립트를 준비했다. 시험 계정 생성과 새 MongoDB 비밀번호의 안전한 입력이 완료되지 않아 API는 아직 시작하지 않았다. 실제 MongoDB 중단·예약 영향은 미측정이며, #17 완료 조건은 충족하지 않았다.

## 재확인 도구

`backend/scripts/measure_event_reliability.py`를 추가했다. 시험 세션 UUID, API 응답의 `accepted` 합계(시도 수), 재전송을 제외한 고유 이벤트 수, 로그 경로를 주면 로그·MongoDB의 고유 ID, 아직 로그에만 있는 건수, 초과 저장 수, 복구 뒤 유실률을 읽기 전용으로 출력한다. 생성기가 직접 넣은 문서는 제외한다. 동일 요청 재전송 세션에는 `--accepted 2 --expected-unique 1`을 넣어 유실 0·초과 저장 1, 장애 복구 세션에는 `--accepted 5 --expected-unique 5`를 넣어 유실 0·초과 저장 0을 확인했다. 고유 이벤트 수를 모르면 유실률을 계산하지 않는다. 실행 환경의 `MONGO_URL`·`MONGO_DB`는 로컬 설정에서 읽으며 결과 문서에 비밀값을 남기지 않는다.
