# F-60 · 이슈 #17 실제 MongoDB 중단·복구 측정 (2026-11-08)

상태: `.40` MongoDB 서비스 중단 중 이벤트 수집·예약 성공과 복구 후 재적재를 확인했다. 109 서버의 400명 동일 부하 재시험은 아직 남았다. 이전 API 연결 불가 모의 시험과 기준은 [11-07 측정](측정_2026-11-07.md)에 기록했다.

## 시험 환경과 시간

- 별도 API `127.0.0.1:8002`가 MariaDB `100.100.100.31/spacecube_test`, MongoDB `100.100.100.40/space_rental_analytics_test`, 전용 임시 `events.log`를 사용했다. MariaDB 제한 계정 준비 스크립트의 완료 출력은 사용자가 확인했다. API 정상 시 `/health=ok`, 시험 DB의 공간 0건을 확인한 뒤 합성 공간 613과 합성 회원 1617을 만들었다.
- 사용자가 `.40` VM에서 `sudo systemctl stop mongod`와 `start mongod`를 실행했다. 첫 `mongo=down` 관찰은 **00:02:15 KST**, 마지막 `down` 관찰은 **00:17:55 KST**였다. 첫 복구 관찰은 **10:46:01 KST**에 `/health=ok`와 TCP 27017 연결 성공이었다. 실제 서비스 시작·종료 시각은 서버 로그로 확인하지 못했으므로 정확한 중단 시간은 미측정이다. 적어도 15분 40초 연속 중단은 API 관찰로 확인했으며, 계획한 5분보다 길었다.
- 장애 중 `/health`는 `degraded`, `mongo=down`이었고 `.40:27017` TCP 연결도 실패했다. 서비스 프로세스 중단 명령은 사용자 보고이며 API와 포트 관찰이 중단 상태를 뒷받침한다.

## 남은 판정

- PM이 공유한 109 서버 400명 부하에서는 기존 코드의 파일 기록 실패가 3/20,936건이었다. 이 브랜치의 잠금 대기 0.5초·실패 지표를 같은 부하 조건에서 재시험해야 개선 효과와 예약 응답 지연을 판정할 수 있다. 공유 작업판 예약과 기존 부하 잠금 해제가 선행 조건이다.
- 109 재시험은 PM의 5+5 풀·동일 배포 상태를 기록하고 이 브랜치의 A 변경만 반영한 뒤, 실제 참여 인원·준비/예열 오류·예약 201과 200을 구분해 측정한다. 양쪽 API 워커의 파일 실패 지표·안전 필드 앱 로그, 고유 로그 ID·MongoDB ID, 예약 생성/취소 수와 예약 p95를 같은 run_id·시간 구간으로 대조한다. 파일 실패가 0인지, 로그 재적재 뒤 누락/중복이 0인지 확인한다. PM의 실행기·109 작업판 담당과 함께 진행한다.
- 시험용 MariaDB 회원 1617·공간 613·예약 4324, MongoDB의 합성 문서와 전용 임시 로그는 결과 확인을 위해 현재 남아 있다. API 시험용 키가 채팅에 노출돼 PID 105240의 별도 API를 종료했고 해당 키를 재사용하지 않는다. DB 비밀번호나 토큰은 이 문서에 기록하지 않았다.
