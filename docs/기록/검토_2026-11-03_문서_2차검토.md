# 문서 2차 검토 (11-03 확정안 전체 + 프로젝트 바깥 시점)

2026-11-03 · 대상: `AGENTS.md`·`STRUCTURE.md`·`STATE.md`, `docs/산출물_01~04`, `docs/백엔드_A·B`, `docs/오류코드.md`, `docs/프론트_변경목록_11-03.md`, `docs/db/*`, 폴더별 README · 방법: 주장–근거 대조(같은 규칙이 문서마다 같은지), 파트 경계에서 값이 이어지는지, 프로젝트 밖(사용자·운영·법·발표) 시점

## 1. 결론

설계의 뼈대(예약 한 트랜잭션, 1062 → 409, primary/replica 경로, 로그 파일 + MongoDB)는 문서끼리 맞고 근거도 있습니다. 이번 검토에서 **파트 경계에서 값이 끊기는 곳 1건**(서버·프론트 이벤트의 세션 id)과 **규칙이 두 곳에서 다른 곳 3건**을 찾았습니다. 바로 고칠 수 있는 6건은 고쳤고, 사람이 정해야 할 9건은 `STATE.md` 열린 질문으로 옮겼습니다. DDL이 실행 검증 전이라는 것이 여전히 가장 큰 불확실성입니다.

## 4. 프로젝트 바깥 시점에서 아직 아무도 말하지 않은 것

| 영역 | 빠진 것 | 왜 필요한가 | 제안 |
| --- | --- | --- | --- |
| 협업 | git 저장소·브랜치·리뷰 방식 | 4명이 `main.py`·문서를 같이 고침. 압축본으로는 누가 무엇을 바꿨는지 못 봄 | GitHub 저장소 + `main` 보호 + 파트별 브랜치 + PR 리뷰 1명 + Actions에서 `verify.ps1` |
| 발표 | 3일차 시연 시나리오 | 무엇을 어떤 순서로 보여 줄지 없으면 당일 데이터·계정이 꼬임 | `docs/시연_시나리오.md`: 시연 계정, 지난 시간 예약 → 바로 후기, 동시 50건 Locust, Grafana 화면 순서 |
| 운영 | 배포·되돌리기·장애 대응 순서 | replica·MongoDB가 죽었을 때 무엇을 보는지, 비용이 나가는 것을 끄는 순서 | `infra/aws`에 런북 한 장(배포 → /health → Grafana 확인, 끄는 순서, replica 삭제) |
| 비밀값 | `.env` 값을 팀이 어떻게 나눌지 | 파일로 돌리면 유출, 각자 다르면 연결 실패 | 팀 채널 비밀 메시지 / 비밀번호 관리자 중 하나로 정하고 `.env.example`과 키 이름 맞추기 |
| 데이터 | 시연용 계정·공간·예약 seed | 매번 손으로 만들면 시연이 흔들림 | `db/seed`에 시연 계정 1~2개(비밀번호는 `.env`), 공간 20개 |
| 법 | 크롤링 약관 최종 확인(06 조사는 '지금은 두기'로 보류) | 발표·공개 저장소에 크롤링 결과가 들어감 | 발표 전 약관 다시 확인, 저장소에는 표본 원문 대신 가공값만 |
| 법 | 개인정보 필수 동의(위 4번) | 생년월일·성별 수집 | 위 결정 |
| 보안 | HTTPS(위 3번), 요청 제한(6번), 의존성 취약점 검사 | 공인 IP로 열림 | `pip-audit`·`npm audit`를 `verify.ps1`에 넣을지 결정, 백엔드 코드 뒤 `ecc-security-review` 스킬로 점검 |
| 측정 | NFR(응답 시간 등)의 목표 숫자 | 'replica가 빠른가'를 Locust로 비교한다고 했지만 합격선이 없음 | p95 목표(예: 조회 300ms, 예약 500ms)를 `산출물_01` NFR에 숫자로 |
| 이름 | '공간큐브' 가칭 | 발표·도메인에 쓰면 겹치는 이름이 있는지 | 발표 전 검색 한 번 |
| 도구 | 개인 스킬 저장소 push | 다른 PC에서 새 스킬 5개가 안 보임 | 사용자가 정함(push) |
