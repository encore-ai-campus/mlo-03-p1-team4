# PRO_1 회의 — 가상 데이터와 크롤링

2026-10-30 · 노진산

스터디룸 예약 서비스의 가상 데이터는 간단한 규칙 기반으로 만들어 수집·분석 구조 검증에만 쓰고, 남는 시간은 예약 동시성과 AWS 부하분산에 쓰는 방향으로 모이고 있습니다. 실제 시장 데이터는 공개 공간대여 페이지 크롤링으로 보완할 수 있습니다.

## 쟁점 정리

단순한 가상 사용자는 빈 시간에 무조건 예약하는 예약봇처럼 움직여 결국 모든 칸이 차고, 그렇게 쌓인 선호도 데이터는 의미가 약하다는 것이 핵심 우려입니다.

| 쟁점 | 제기된 내용 | 제안된 대응 |
| --- | --- | --- |
| 예약봇 데이터 | 성공할 때까지 재시도하면 모든 빈 칸이 예약됨 | 선호 요일·시설·시간이 안 맞으면 예약을 포기 |
| 시간 축 | 하루치만으로는 패턴이 안 보임 | 가상 날짜를 넘기며 4주치 기록 생성 |
| 사용자 규모 | 공급(하루 열리는 칸 수)과 수요가 안 맞으면 왜곡 | 하루에 열리는 칸 수에 맞춰 가상 유저 수 설정 |
| 실패 로그 | 예약 성공만 남기면 탐색 행동이 사라짐 | 상세 조회, 가능 시간 확인, 예약 포기도 이벤트로 저장 |
| 데이터 용도 | 가상 데이터로 실제 선호를 찾았다고 주장하기 어려움 | 수집·분석 구조가 제대로 도는지 검증하는 용도로 한정 |
| 작업 비중 | 시뮬레이션에 공을 들이면 본 프로젝트가 밀림 | 규칙 기반으로 단순하게 두고 동시성·AWS 부하분산에 시간 배분 |

가상 기록은 실제 사용자 데이터와 구분해 저장합니다(예: `is_synthetic` 컬럼 또는 별도 테이블).

## 시뮬레이션 최소 설정안

가상 사용자는 4개 유형으로 나누고, 유형마다 선호 시간·룸과 포기 조건만 정합니다. 비율과 조건 값은 회의에서 정할 초안입니다.

| 유형 | 비율(초안) | 선호 시간·요일 | 선호 룸 | 포기 조건 |
| --- | --- | --- | --- | --- |
| 대학생 | 35% | 평일 오후, 시험 기간 오전 | 101 1인 부스, 102 페어룸 | 선호 시간대에 빈 칸이 없으면 |
| 직장인 | 25% | 평일 19시 이후, 주말 오전 | 101, 302 라운지 | 퇴근 시간대가 아니면 |
| 스터디 모임 | 20% | 주말 오후, 평일 저녁 | 201 그룹룸, 202 세미나룸, 301 회의실 | 인원에 맞는 룸이 없거나 2시간 연속이 안 되면 |
| 단순 탐색자 | 20% | 아무 때나 | 없음 | 항상 예약 없이 종료 |

행동 규칙은 네 가지로 제한합니다.

1. 방문자의 일정 비율은 예약 없이 탐색만 하고 종료한다.
2. 선호 룸·요일·시간이 맞지 않으면 예약하지 않는다.
3. 예약에 실패하면 대안 탐색은 최대 1~2회로 제한한다.
4. 부하테스트용 예약 기록과 분석용 데이터는 분리한다.

저장할 이벤트: 메인 방문, 검색(날짜·시간 / 번호·유형), 룸 상세 조회, 시간 칸 선택, 예약 시도, 예약 성공, 중복 차단, 예약 포기.

도구는 두 가지를 검토 중입니다. Playwright는 테스트별 조건 설정과 병렬 실행을 지원하고, Locust는 가상 사용자 종류·비율·대기시간·동시 접속자 수를 설정할 수 있습니다. 위 유형·비율은 Locust의 사용자 클래스와 가중치로 그대로 옮길 수 있습니다.

## 웹 크롤링 후보

스페이스클라우드 공간 상세 페이지(`/space/<id>`)에서 가격·인원·시설·후기를 모을 수 있고, 가상 룸과 사용자 선호 설정의 근거로 쓰기 좋습니다. 다만 실제 예약 현황은 크롤링으로 얻을 수 없습니다.

| 수집 항목 | 페이지 위치 | 우리 프로젝트 활용 |
| --- | --- | --- |
| 시간당 가격, 패키지 가격, 최소 예약시간 | 상세 · 세부공간 선택 | 가상 룸 6개의 가격·최소 이용시간 근거 |
| 수용인원(최소~최대), 공간면적(㎡) | 상세 · 요약 정보 | 1인실·소형·중형·대형 구분 기준 |
| 공간유형(회의실·파티룸·스터디룸), 해시태그(#팀플 #면접 등) | 상세 상단, 목록 카드 | 이용 목적 분류, 사용자 유형별 선호 목적 |
| 편의시설 아이콘(화이트보드, TV/프로젝터, WiFi, 주차 등 18종) | 상세 · 시설 아이콘 | 검색 필터 항목, 선호 시설 변수 |
| 영업시간, 휴무일 | 공간 소개 | 운영시간 설정 |
| 환불 규정(이용 n일 전 %) | 환불정책 탭 | 비어 있는 우리 취소·환불 정책 초안 |
| 후기 수, 평균 평점, 후기 본문, 작성 일시 | 이용후기 탭 | 후기 키워드 분석, 작성 요일·시간대를 이용 시간대의 간접 지표로 |
| 좋아요 수, 리뷰 수 | 목록 · 비슷한 공간 카드 | 인기도 지표 설계 참고 |
| Q&A 질문 | Q&A 탭 | 사용자가 자주 묻는 정보(주차, 장비) |
| NOW 바로결제, 쿠폰할인, AD 배지 | 목록 카드 | 프로모션 여부 변수 |

수집 전에 지킬 것:

- robots.txt는 모든 봇에 `/search*`, `/reserve/`, `/my/`, `/auth/login`을 막고, `/space/<id>` 상세 페이지는 허용합니다. 예약 가능 시간·예약 현황은 막힌 경로라 수집 대상이 아닙니다.
- 목록은 자바스크립트로 그려져 상세 링크를 모으려면 Playwright 같은 브라우저 렌더링이 필요합니다.
- 이용약관에 크롤링을 직접 금지하는 조항은 없지만, 제11조가 동의 없는 영리 목적 사용과 부당한 행위를 금지합니다. 수업용으로만 쓰고, 요청 간격을 두고, 수집 범위를 작게 잡습니다.
- 후기 작성자 닉네임은 저장하지 않고, 후기 본문은 통계·키워드 분석에만 씁니다(원문을 우리 서비스에 옮겨 싣지 않음).

대안으로 서울 열린데이터광장의 공공서비스예약(시설대관) OpenAPI는 공공누리 1유형이라 약관 걱정이 없고, 서비스 상태·장소·접수 기간을 제공합니다. 크롤링 대신 또는 함께 쓸지 회의에서 정합니다.

## 유사 서비스와 id 수집 가능 여부

공간 id로 상세 페이지를 열 수 있고 robots.txt가 허용하는 곳은 스페이스클라우드와 쉐어잇입니다. 두 곳 모두 사이트맵에 공간 id 목록이 있어, id를 하나씩 대입해 볼 필요 없이 사이트맵만 비교하면 새로 생긴 공간을 찾을 수 있습니다.

| 서비스 | 상세 URL 형식 | robots.txt (일반 봇) | 사이트맵 | 판단 |
| --- | --- | --- | --- | --- |
| [스페이스클라우드](https://www.spacecloud.kr/sitemap.xml) | `/space/<id>` | 상세 허용, 검색·예약 차단 | 공간 14,137개(후기 URL 2만 개 별도), 최대 id 82391, lastmod 최신 2026-10-29 | 주 대상 |
| [쉐어잇](https://shareit.kr/sitemap.xml) | `/venue/<id>` (호스트 `/store/<id>`) | 일부 경로만 차단 | 공간 사이트맵 있음, lastmod 없음 | 보조 대상 (대학·기관 공간이 섞임) |
| [서울시 공공서비스예약](https://yeyak.seoul.go.kr/robots.txt) | 서비스 id(`rsvsvcid`) | 게시판만 차단 | — | OpenAPI로 받기 |
| [아워플레이스](https://hourplace.co.kr/robots.txt) | — | 전체 차단(`Disallow: /`) | 검색엔진 전용 | 제외 |
| [네이버 예약](https://booking.naver.com/robots.txt) | — | 전체 차단(`Disallow: /`) | — | 제외 |

## 신규 오픈 룸 확장 아이디어

크롤링할 때마다 새 공간을 찾아 우리 서비스에 '신규 오픈' 룸을 늘리는 것은 가능합니다. 단, 가져온 사진을 그대로 올리지 않고 속성만 가져와 가상 룸을 만드는 방식을 제안합니다.

1. 주 1회 사이트맵을 받아 지난번에 없던 공간 id를 찾는다.
2. 새 id의 상세 페이지에서 공간유형·수용인원·시설·가격대만 수집한다(스터디룸 유형만).
3. 그 속성으로 가상 룸(예: 303호)을 만들고, 이미지는 우리 일러스트(인원·시설에 맞는 유형)나 무료 라이선스 사진으로 붙인다.
4. 메인에 NEW 배지를 달고, 출처 id는 내부 컬럼에만 남긴다.

사진을 그대로 쓰지 않는 이유:

- 공간 사진의 저작권은 호스트(또는 플랫폼)에 있어, 복제해 게시하면 수업용이라도 문제가 될 수 있습니다.
- 다른 업체의 실제 공간 사진을 우리 룸인 것처럼 보여주면 사용자를 속이는 화면이 됩니다.
- 사진을 원본 주소로 바로 불러오면 상대 서버에 부하를 줍니다.

이 방식은 주기 배치 파이프라인(수집 → 변환 → 적재)이 되고, 신규 룸이 들어오면 시뮬레이션 수요도 바뀌어 데이터가 덜 정적이 됩니다. 룸이 계속 늘면 가상 유저 수도 함께 늘려야 하므로, 최대 룸 수나 주당 추가 개수는 회의에서 정합니다.

이미지는 미리 만들어 둔 일러스트 풀을 순환시켜 붙이기로 했습니다(10/30). 신규 룸은 'NEW 스터디룸'으로 메인에 따로 보여줍니다.

| 크롤링한 공간 조건 | 붙일 이미지 풀 |
| --- | --- |
| 최대 1~2인 | 1인 부스 |
| 최대 3~4인 | 2인 페어룸, 창가 라운지 |
| 최대 5~8인 | 4인 그룹룸, 6인 세미나룸 |
| 최대 9인 이상 | 10인 회의실 |

- 같은 풀 안에서는 순서대로 돌려 연달아 들어온 신규 룸이 같은 그림을 쓰지 않게 합니다.
- 풀이 작아 같은 그림이 자주 보이면 벽·바닥 색만 바꾼 변형을 더 만듭니다(일러스트는 코드로 그려져 색 변형이 쉽습니다).
- 화이트보드·TV·빔프로젝터 같은 시설 여부는 이미지가 아니라 룸 정보의 시설 태그로 보여줍니다.
- NEW 배지는 등록 후 14일 동안 달고, 그 뒤에는 일반 룸 목록에 합칩니다(`공간대여_01_기능정의.md` F-14, DB `new_until`).
