# 가상 날짜 도입 시 담당별 고려사항

가상 날짜는 `.env`가 아닌 DB에 저장하고, API를 통해 하루씩 이동시키는 방식으로 생각하고 있습니다. 시간까지 가상으로 운영하는 건 아니고, 날짜만 변경하는 방식입니다. 예를 들어 가상 날짜가 11월 3일이라면 3일부터 14일간 예약할 수 있고, 다음 날로 이동하면 4일부터 새로운 14일이 열리는 식입니다.

### 이 방식은 다음과 같은 원칙을 지킵니다

1. **가상 날짜만 사용하고 가상 시각은 사용하지 않는다.** 가상 날짜는 DB에 저장하며, API를 통해 하루 단위로 이동시킨다.
2. **서비스 운영에 필요한 날짜 판단은 가상 날짜를 기준으로 한다.** 예약 가능 기간, NEW 표시, 인기순 집계, 예약 완료 처리 등이 해당하며, 날짜 이동에 따른 상태 변경도 일자 단위로 처리한다.
3. **실제 시각은 그대로 유지한다.** 회원가입·예약·결제 등의 발생 시각, 사용자 행동 순서, JWT 만료 등은 실제 시간을 사용한다.
4. **사용자 활동 로그에는 실제 발생 시각과 당시의 가상 날짜를 함께 기록한다.** 이를 통해 실제 시간 기준의 행동 흐름과 가상 날짜별 가입·조회·예약 등의 통계를 모두 분석할 수 있도록 한다.

### 프론트엔드

예약 달력은 실제 오늘이 아니라 서버에서 전달받은 가상 날짜를 기준으로 표시해야 할 것 같습니다. 예약 가능한 날짜나 시간대, NEW 표시, 예약 상태 등의 판단과 갱신은 백엔드에서 처리하므로 프론트에서는 API 응답에 맞춰 화면을 구성하면 될 것 같습니다. 다만 날짜 선택이나 검색 조건 등 프론트에서 직접 날짜를 다루는 부분에는 가상 날짜가 적용되도록 신경 써야 할 것 같습니다.

### 백엔드 A (회원·후기·게시판·로그)

회원가입이나 로그인, 토큰 만료 같은 기능은 기존처럼 실제 시간을 기준으로 처리하면 될 것 같습니다. 다만 나중에 데이터를 분석할 때 가상 날짜별 가입자 수나 로그인 횟수, 페이지 조회 수 등을 확인할 수 있도록 **사용자 활동 로그에는 실제 발생 시각과 당시의 가상 날짜를 함께 기록**하면 좋겠습니다. 후기 작성은 예약 상태와 관련이 있으니, 가상 날짜가 이동하면서 예약이 완료 처리되는 부분을 B와 맞춰야 할 것 같습니다. (이부분은 가상 날짜가 11월 14일로 변경되면 13일 이전의 예약확정인 건들을 완료 처리하는 방식이 어떨까 합니다.)

### 백엔드 B (공간·예약·결제·크롤링)

예약 가능 기간이나 취소 가능 여부를 가상 날짜로 판단해야 하고, 날짜가 넘어가면 이전 날짜의 예약들을 완료 처리해야 합니다. NEW 표시나 인기순 집계도 가상 날짜를 기준으로 계산해야 할 것 같습니다. 날짜를 이동시키는 API도 필요하고, 크롤링 또는 가상 생성해 등록하는 신규 공간을 어느 시점에 공개할지도 함께 고려해야 합니다.

### DB

현재 가상 날짜를 저장할 테이블이 필요합니다. 그리고 기존 데이터 중에서 실제 시각과 가상 날짜를 따로 저장해야 하는 항목이 있는지도 살펴봐야 할 것 같습니다. 예를 들어 사용자 활동과 별개인 venues 테이블에서는 공간의 신규 등록일(created_at 컬럼)은 가상 날짜로 저장해도 괜찮아 보이지만, reservations 테이블의 경우에는 예약이 발생한 실제 시각과 가상 날짜를 함께 저장하는 것이 좋아 보입니다. 날짜가 이동하더라도 기존 예약이나 활동 데이터는 분석에 사용할 수 있도록 유지하는 방향이 좋을 것 같습니다.

### 함께 이야기해 볼 부분

가상 날짜를 이동시킬 때 예약 완료 처리를 함께 진행할지, NEW 표시와 인기순의 날짜 기준을 어떻게 잡을지, 크롤링 또는 가상 생성으로 추가되는 공간을 언제 추가할지 등을 정하면 좋겠습니다. 특히 **가상 시간까지 구현하는 것은 아니므로 예약은 기존처럼 시간대를 선택하되, 날짜 이동에 따른 상태 변경은 하루 단위로 처리**하는 방향으로 생각하고 있습니다.

이 외에도 각자 담당하는 기능에서 날짜가 바뀌면서 영향을 받는 부분이 있는지 한번 살펴보고 이야기해 보면 좋겠습니다.
