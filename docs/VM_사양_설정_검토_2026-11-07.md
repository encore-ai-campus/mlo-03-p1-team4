### 우선순위

1. **먼저 계측을 늘린다. 동작은 바꾸지 않는다.**
   - 503이 어디서 났는지 가를 숫자가 없다. 지금은 풀 대기, DB 연결 오류, 헬스체크가 모두 같은 503으로 보인다.
   - 앱(A 담당 `core/db.py`·`errors.py`)에 아래 세 가지를 추가하자고 제안한다.
     - 풀 checkout 대기 시간 히스토그램
     - 503을 원인별로 센 카운터(`pool_timeout` / `db_connect` / `health`)
     - 스레드 풀 사용 중 개수
   - 이게 없으면 아래 조정은 모두 추측이다.
2. **스레드 풀 동시성(40)과 DB 풀(5)을 맞춘다.** [가설·유력]
   - 워커 하나가 동기 요청을 최대 40개 동시에 받는데, DB 연결은 엔진마다 5개뿐이다.
   - 그래서 부하가 오르면 대기가 풀 앞에 쌓이고, 3초를 넘으면 503이 된다.
   - 근거
     - 쓰기 400에서 Uvicorn 경고 0, HAProxy DOWN 0인데 JSON 503이 났다.
     - DB 연결 최고 15~23으로 한도 151에 한참 못 미쳤다.
     - 쓰기 200의 예약 p95가 1,022ms로 튀었다.
   - 아래 후보 중 **하나씩만** 시험한다.
     - (a) `pool_size 3→5, max_overflow 2→5`. 엔진·워커당 10, primary 이론상 최대 40으로 151 안쪽이다.
     - (b) 스레드 풀 크기를 풀 크기에 가깝게 줄인다(예: 워커당 10~15). 넘치는 요청은 빨리 실패하거나 대기열로 보낸다.
     - (c) `pool_timeout` 3초는 유지한다. 늘리면 503은 줄지만 p95가 나빠지고 원인이 가려진다.
3. **HAProxy에서 대기열로 받는다.** [가설]
   - 서버별 `maxconn`(예: 앱 VM당 60~80)과 `timeout queue 5s`를 두면, 넘친 요청이 앱 안에서 503이 되지 않고 gw에서 줄을 선다.
   - `/health`가 바쁜 스레드 풀 뒤에서 늦게 응답해 앱이 빠지는 문제(읽기 400에서 api1이 6.14초 제외됨)는 둘 중 하나로 다룬다.
     - 헬스를 비동기 경량 경로로 바꾸기
     - `fall 3`과 `timeout check`를 명시하기
   - 결제 POST 재전송을 막는 `retries 0`은 유지한다.
   - global `maxconn`도 명시한다. gw RAM이 768MB라서다.
4. **Uvicorn 워커와 limit-concurrency**
   - vCPU 1개에 워커 2개는 I/O가 섞인 부하에서 무난하다. vCPU를 늘리기 전에는 워커를 늘리지 않는다.
   - `limit-concurrency 200`은 스레드 풀(40×2)보다 커서 대기만 길게 만든다. 2·3을 반영한 뒤 100 정도로 낮출지 비교한다.
5. **MongoDB 디스크를 확장한다. 필수, 성능과는 별개다.**
   - 루트 LV가 9.8G에 여유 2.2G뿐이다.
   - 내일부터 크롤링·Playwright 이벤트를 쌓기 전에, 남은 VG 공간으로 LV를 늘린다(VG 여유는 sudo가 필요해 미확인). 남은 공간이 없으면 VMDK 확장이 필요하다.
   - MongoDB exporter를 붙인다. 캐시는 기본값을 유지한다(데이터가 작다).
6. **Loki·Prometheus 보존 기간을 늘린다.**
   - 지금 48h / 2d라서, 토요일 시험 원본 로그·지표가 **월요일 오후 발표 전에 지워질 수 있다.**
   - mon 디스크 여유가 13G이니 Loki 96h, Prometheus 4d / 4GB 정도로 늘린다. 시험 ZIP은 이미 따로 보존돼 있다.
7. **MariaDB는 유지하고 관측만 보탠다.**
   - buffer pool 128MB는 데이터 6.4MB 대비 충분하다(buffer pool 디스크 읽기 비율 약 0.006%).
   - replica의 디스크 임시 테이블 13,320건은 시험 중에만 `slow_query_log`(`long_query_time` 0.2)를 켜서 원인 조회를 찾은 다음 판단한다. `tmp_table_size`를 바로 올리지 않는다.
   - `max_connections` 151, `flush_log_at_trx_commit=1`은 유지한다.
   - `sync_binlog=0`은 장애 때 binlog 일부를 잃을 수 있다는 점만 기록한다(시연 범위에서는 유지).
8. **Nginx는 유지한다.**
   - 400 VU에서 `worker_connections` 768 / ulimit 1024는 여유가 있다.
   - 접근 로그 `buffer=32k flush=1s`는 디스크 busy가 1% 미만이라 효과가 작다. 후순위다.

## 5. 관측 한계

- **사고 기록**

- 읽기(이전 배포 `1583778`, 공간 19)와 쓰기(로컬 브랜치, 공간 31, keepalive·타이머 적용)는 배포와 데이터가 달라 **직접 A/B 비교를 할 수 없다.**
- 1분 평균 CPU는 순간 포화를 숨긴다. 1초 SSH 표본(api 최고 64.95~68.37%)도 스크랩 사이를 다 보지 못한다.
- MongoDB는 exporter가 없고, sudo 비밀번호가 필요해 데이터 크기와 볼륨 그룹 여유를 확인하지 못했다.
- DB 풀 대기, 스레드 풀 사용, VM steal time은 계측하지 않았다. 디스크 지연·IOPS·iowait 분리 기록도 없다.
- 쓰기 400은 실제 398명이었고, 기존 예약 200 응답이 91건 섞였다. **정상 400명 처리 용량으로 판정하지 않는다.**

## 6. 사실과 가설

**[사실]**
- 쓰기 100은 오류 0, 예약 201 p95 64.93ms다.
- 쓰기 200은 오류 0이지만 예약 p95 1,022.31ms로 500ms 기준을 넘었다.
- 쓰기 400 목표는 로그인 503 2건, 워밍업 503 18건으로 실패했다.
- 모든 VM에서 CPU·RAM·디스크가 계속 포화되지는 않았다(api 1분 평균 최고 약 65%, 디스크 busy 1% 미만).
- DB 연결은 한도보다 훨씬 낮았다.
- Mongo 루트 여유 2.2G, Loki 48h·Prometheus 2d 보존, 현재 설정값(2절 표)은 직접 확인했다.

**[가설]**
- 503과 200명 p95 급등의 주된 원인은 **앱 DB 풀 대기**다(풀 5 대 스레드 40). 순간 CPU 포화와 헬스체크 지연도 원인일 수 있다.
- 2 vCPU 증설의 효과는 계측 전에는 알 수 없다.
- 한 번의 측정으로 "최적 사양"을 정하지 않는다. 0번 반복으로 편차를 본 뒤, 1~4번을 하나씩 비교해 판단한다.
