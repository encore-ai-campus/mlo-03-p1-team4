## 해석과 다음 검토

보조 발생기/물리 호스트 표본은 수집기 수정 후 18:41 KST부터 보존됐으므로 100명 구간 전체를 포함하지 않는다. VM 7대 기본 자원 기록은 시험 시작부터 유지했다. CPU는 Prometheus 1분 평균의 최고값이고, Mongo는 약 30초마다 얻은 1초 SSH 표본이다. 순간 피크·짧은 잠금은 놓칠 수 있다. Mongo 디스크 I/O는 100명 종료 뒤부터 추가했으므로 100명 표본은 N/A다. 디스크 상세 IOPS·처리량·평균 I/O 시간·iowait·스왑은 prometheus-range.json에 보관했다.

- 소프트웨어/하드웨어를 이번에 조정하지 않았다. CPU·RAM·디스크 여유와 지연이 모두 양호하면 증설이나 동시성 제한 상향을 먼저 할 근거가 약하다. 읽기 결과만으로 쓰기 여유를 보장하지 않는다.
- 앱 DB 풀 획득 대기는 현재 계측하지 않았다. DB 연결/행 잠금 표본이 낮다고 풀 대기가 전혀 없었다고 단정하지 않는다.
- FastAPI 지표는 현재 scrape에 잡힌 워커 기준이다. 전체 요청 판정은 Locust 원본과 두 Nginx 요청 로그를 우선한다.
- 쓰기 확장은 사용자 검토 뒤 진행한다. 계정 공유로 병목을 만들지 않도록 VU당 합성 계정과 독립 시간 칸을 확보하며, 새 설정 적용 전후는 동일 프로토콜로 비교한다.
- 다음 소프트웨어 비교 후보는 대기 중인 #67 Nginx keepalive·request_id/상류 지연 로그다. 먼저 현재 설정의 쓰기 기준선을 확보하고 한 항목씩 A/B 비교한다.
- Claude의 대기 중 Nginx 변경이 적용됐다면 다음 쓰기/설정 비교 전에 지문을 다시 확인하고 변경점을 별도 기록한다.

## 400명 실패 구간 재구성·검토 결론

- 18:49:38부터 시작한 일부 요청이 길어졌고, 18:49:54~18:50:04에 실패 응답이 집중됐다. 전송 실패 147건은 약 20초 지연 양상이지만 현재 원본에는 기저 네트워크 예외 클래스가 없어 실제 원인을 단정하지 않는다.
- 측정 21,279건 중 HTTP 200은 20,901건, 503은 231건, 전송 실패는 147건이다. 오류율 1.7764%다. 503 중 JSON SERVICE_UNAVAILABLE 135건과 일반 응답 96건을 구분했다.
- 성공 요청만의 p95 295.81ms와 달리 **오류 포함 전체 p95 402.29ms / p99 18,576.42ms**다. 400명은 오류율과 전체 지연 기준 모두 미달이다. 성공 요청 통계만 보고 통과라고 판단하지 않는다.
- Uvicorn 동시성 초과 경고는 api1 PID 7891에서 5회, api2 PID 4988에서 95회다. worker 2/limit-concurrency 200/keep-alive 5초는 유지했다. 경고 수는 실패 HTTP 요청 수와 같지 않으며 당시 활성 연결/task 실측 수는 없다.
- HAProxy는 18:50:01.277에 /health 503을 받은 api1을 DOWN 처리했고 18:50:07.414에 200으로 UP 복귀시켰다. 약 6.14초다. api2도 check 실패 카운터가 증가했지만 해당 구간 DOWN 전환은 확인되지 않았다. 15초 UP 표본만으로 짧은 DOWN을 놓칠 수 있어 로그와 누적 카운터를 보완했다.
- FastAPI 요청 로그 61,876행을 안전 필드만 남겨 보존했다. JSON 503 응답 135건은 request_id로 앱 로그와 연결했다. 앱 로그 ms는 응답 뒤 작업/기록까지 포함할 수 있어 클라이언트 응답 시간과 같은 지표로 합산하지 않는다. 현재 앱의 처리된 503 로그에는 세부 예외 유형이 없어 DB 풀 timeout과 접속 오류를 확정 구분하지 못한다.
- 측정 400명에서 CPU 1분 평균 최고 api1 51.62%·api2 51.29%, RAM 최고 42.54%·40.70%, 디스크 busy 최고 0.25%·0.04%다. DB 전체 연결 최고는 primary 18·replica 19로 max_connections 151보다 낮고, 수집 표본의 행 잠금 대기·복제 지연은 0이다. 순간 포화나 앱 DB 풀 대기가 전혀 없었다는 증거는 아니다.
- after100과 종료 후 수집한 앱/프록시/DB 관련 파일 지문은 모두 같았다. 자동 증량은 400명 실패로 종료했고 쓰기는 실행하지 않았다. 시험 종료 뒤 /api/health status=ok를 확인했다.

**이번 조건에서 확인한 최고 통과 단계는 200명이다. 다음 탐색 범위는 200~400명이지만 최대치를 확정한 것은 아니다. 막판 오류가 집중됐으므로 200명 장시간 반복과 400명 재현도 필요하다.** 소프트웨어를 바로 늘리기보다 워커별 연결/task·AnyIO 작업 대기·DB 풀 획득 대기와 세부 503 예외 유형을 계측하는 것이 다음 진단 우선순위다. Uvicorn 제한만 올리면 대기가 더 늘 수 있으므로 CPU/DB 연결 수만 보고 상향하지 않는다. 쓰기 기준 시험을 먼저 할지는 사용자 검토 후 결정한다. Mongo 루트 여유는 약 2.16GiB이므로 대규모 생성기 적재 전 용량 증가도 산정한다.

보조 호스트 기록은 18:41부터이며 첫 표본의 프로세스 CPU 0은 초기화 표본이다. 이 보조 기록으로 100명 구간의 호스트 상태를 주장하지 않는다. VM별 본 수집은 시작부터 유지됐고 수집 오류 표본은 없었다.

설정 의미 참고: [Uvicorn resource limits](https://uvicorn.dev/settings/#resource-limits)는 동시 연결 또는 task 제한 초과 시 503을 반환한다고 설명한다. [SQLAlchemy pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html)은 풀 크기·overflow·획득 timeout을 별도로 다룬다. 이 의미를 현재 503의 최초 원인 확정과 혼동하지 않는다.

400명 구간의 1초 SSH CPU 표본 최고는 api1 64.95%·api2 68.37%였다. 발생기 PC 전체 CPU 최고 14%, Locust 프로세스 최고 22.8%(한 코어 기준), VMware 호스트 CPU 표본 최고 5%·가용 RAM 최소 약 21.54GiB였다. 표본만으로 순간 포화를 배제하지는 않는다. 최종 Grafana 11개 제목·레이아웃·쿼리가 저장 원본과 모두 같았고 19/19 targets UP·gateway health ok를 재확인했다.
