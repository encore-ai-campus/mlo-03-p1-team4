## 부하 결과를 발표할 때

- 11-07의 공개 읽기 400명 실패 구간은 21,279건 중 오류 378건, 전체 p95 402.29ms였다. 성공 요청만의 p95 295.81ms를 전체 성능으로 말하지 않는다. 출처: `docs/읽기부하_100_200_400_검토_2026-11-07.md`.
- 이후 DB 풀 5+5 읽기 100/200/400명은 오류 0, p95 71/70/98ms로 팀 공유 문서에 기록됐다. 배포·데이터·Nginx 조건이 달라 한 변수만 바꾼 A/B 시험으로 해석하지 않는다. 출처: `docs/부하실험_이벤트기록_팀공유_2026-11-08.md`.
- 같은 문서의 쓰기 400명 오류 0과 예약 POST p95 286ms는 측정 기록이다. 이벤트 파일 append 실패 3건은 HTTP 오류 0과 별개다. 11-08 문서에는 600명 쓰기에서 append 실패 17건도 기록됐다.
- 500/600/800명 공개 GET은 오류 0, p95 81.6/85.4/227.2ms다. 800명은 API 평균 CPU 50~60% 목표를 넘었고, 공개 GET 시험이 예약 쓰기 처리량을 입증하지는 않는다.
- README의 1,000명 결과와 파일·MongoDB 21,374건 일치 수치는 원본 시험 조건·대사 범위를 이 브랜치에서 확인하지 못했다. 수치를 지우거나 새로 재현했다고 주장하지 않고, 원본이 확인될 때까지 기존 기록으로만 인용한다.

## 실제 결과를 채우는 순서

1. 운영 DB의 시점·스키마 버전·실행 커밋과 분석 기간을 기록한다. 읽기 전용 계정으로 `db/queries/reservation_quality.sql`을 먼저 실행한다. 오류 항목이 0이 아니면 판매·이용 숫자를 확정하지 않는다.
2. SQL 3개를 같은 합성 데이터 조건으로 실행하고 결과 표와 전체 예약·결제 건수를 보존한다. 합성/실사용 데이터를 한 숫자로 섞지 않는다.
3. `event_behavior.js`를 같은 기간의 `occurred_at` 범위로 실행한다. 이벤트 건수와 고유 세션 수를 별도 표시하고, 브라우저 세션과 서버 이벤트의 연결 가능 여부를 확인하기 전에는 전환율을 쓰지 않는다.
4. 같은 테스트 실행 ID·시간창에서 보낸 이벤트 수, `events.log`의 `event_id`, MongoDB `events.event_id`를 대조한다. 생성기가 MongoDB에 직접 쓴 과거 이벤트는 API 전달률에서 제외한다.
5. NFR-05를 판정하려면 동시 50명·각 단계 10분(첫 1분 제외), 조회/예약/로그인별 p95와 오류율을 Locust 원본으로 확인한다. 저장소의 60초 선별 CSV는 이 판정을 대신하지 않는다.

## 이번 브랜치의 로컬 검증

- SQL 4개는 `sqlglot`의 MySQL 문법 파싱을 통과했다. 이는 MariaDB에서 쿼리를 실행해 결과를 검증한 것은 아니다.
- `event_behavior.js`는 `node --check`를 통과했다. MongoDB 연결·실제 집계 결과는 확인하지 않았다.
- 프로젝트 지정 conda 환경 `mlo-03-p1-team4`에서 Ruff 전체 린트와 174개 Python 파일 포맷 검사를 통과했다.
- 저장소의 `verify.ps1`은 현재 PC의 `pro_1` 환경 대신 기본 Python을 선택해 Ruff·pytest 모듈을 찾지 못했고, 프론트 의존성의 `run-s`도 없어 실패했다. 프론트 코드는 이번 브랜치에서 변경하지 않았다. 전체 pytest와 프론트 verify의 통과를 주장하지 않는다.
