강사님이 주신 고려사항(인공지능 활용, 서버 구성, 서비스 구현, 자동화 구현, 데이터)에 다락큐브 기준으로 답합니다. 표의 '정한 것'은 이미 문서·코드에 반영된 결정이고, '제안'은 팀 확인이 남은 것입니다.

## 1. 인공지능 활용

### 1-1. AGENTS.md는 어떻게 설정하나

**저장소 루트 `AGENTS.md` 하나 + 파트 폴더마다 `AGENTS.md`**(정한 것). Codex와 Claude Code가 같은 파일을 읽습니다. `CLAUDE.md`는 따로 만들지 않습니다(두 도구가 다른 규칙을 보지 않게).

| 항목 | 루트 `AGENTS.md`에 적은 것 |
| --- | --- |
| 공통 규칙 | 바꾸면 안 되는 도메인 규칙(예약 단위 `venues`, 실제 날짜, 한 트랜잭션, 1062 → 409, 상태 3개, 모의 결제, 이벤트 저장 순서) |
| 구조 | 기준 문서 표(무엇은 어느 문서가 이기나), 폴더와 담당 표, 파트 사이 약속(함수 이름·인자·반환) |
| 작업 순서 | ① `STATE.md`(상태·열린 질문) → ② `STRUCTURE.md`(담당·기준 문서) → ③ 작업 폴더 README·AGENTS → ④ 필요한 기준 문서만 |
| 완료 시점 | 돌린 테스트와 결과를 그대로 보고, `STATE.md`의 파트 줄·기능 진행표·최근 변경 고침, 새 결정은 결정 기록 + 기준 문서 |
| 금지 사항 | 비밀값 파일·커밋 금지, 로그에 개인정보 금지, AWS 리소스 변경 금지(사람이 함), Docker 무단 실행 금지, 테스트 스키마 밖 `DROP`, 크롤링 20건 초과, 테스트·제약 약화 |
| 큰 버그 규칙 | 읽기 경로(primary/replica), 계층(라우터·서비스·리포지토리), 문서에 없는 표·API·오류 코드 만들지 않기, 정해지지 않은 것은 고르지 않기 |

파트 폴더 `AGENTS.md`(`frontend/`·`backend/`·`db/`·`crawler/`)는 그 폴더 안에서 루트보다 우선합니다(예: `backend/AGENTS.md`의 DB 연결 규칙·연결 수 한도, `crawler/AGENTS.md`의 요청 간격·robots.txt).

### 1-3. 서브 에이전트는 어떻게 구성하나 (제안)

파트 담당과 같게 나누고, **쓰기 권한을 폴더로 제한**합니다. 리뷰어는 읽기만 합니다.

| 에이전트 | 맡는 폴더(쓰기) | 읽는 기준 | 끝날 때 돌리는 것 |
| --- | --- | --- | --- |
| `frontend_dev` | `frontend/` | `프론트_변경목록_11-03`, `백엔드_A·B` 5절, `오류코드` | `npm run verify` (+ 화면 흐름 바꾸면 `test:e2e`) |
| `backend_dev` | `backend/` (A·B 파일 구분은 `STRUCTURE.md`) | `백엔드_A·B`, `산출물_04`, `backend/AGENTS.md` | `ruff`, `pytest backend/tests` |
| `db_dev` | `db/`, `crawler/`, `simulator/generator`, `infra/local` | `산출물_04`, `db/AGENTS.md` | `db/tests/check_ddl.py`, `load_seed.py --check` |
| `reviewer` | 없음(읽기만) | 위 전부 + `오류코드` | 계약(경로·응답·오류 코드·이벤트 이름)과 다른 곳, 큰 버그 규칙 위반, 보안(`ecc-security-review`)을 PR 댓글로 |

- Claude Code는 `.claude/agents/<이름>.md`(쓸 수 있는 도구·폴더를 적음)로, Codex는 같은 역할 설명을 작업 지시 맨 앞에 붙여 씁니다.
- 한 작업에 쓰는 에이전트는 하나, 다른 파트 파일이 필요하면 멈추고 사람에게 알립니다(루트 `AGENTS.md` 규칙과 같음).

### 1-4. 하네스·루프 엔지니어링은 어떻게 하나

**기능 하나 = 한 바퀴**(정한 것: 브랜치·PR, 검증 명령 / 제안: 2번 실패 규칙)

```text
① 브랜치 만들기  develop에서 feat/<파트>-<F-ID>  (예: feat/B-F-30)
② 구현          해당 에이전트가 담당 폴더만 고침
③ 검증          verify.ps1(ruff → pytest → 프론트 verify) + 파트 시험(check_ddl 등)
④ 커밋·푸시     [파트] F-ID 요약
⑤ PR           develop으로, reviewer 에이전트 + 팀원 1명 리뷰
⑥ 머지          develop에 합침(마일스톤 끝에 develop → main) → STATE.md 기능 진행표 갱신 → 다음 기능
```

**검증이 같은 원인으로 2번 실패하면 멈추고 하네스를 고칩니다**(제안).

| 상황 | 하는 일 |
| --- | --- |
| 1번째 실패 | 에이전트가 오류를 읽고 고쳐 다시 검증 |
| 2번째 실패 | 더 고치지 않고 멈춤. 실패 명령·오류 줄·추정 원인을 `STATE.md` 열린 질문에 적고 사람에게 넘김 |
| 같은 종류가 다시 나오면 | 그 실수를 막는 장치를 하네스에 더함: `AGENTS.md` 규칙 한 줄, 검사 스크립트(예: 이번에 넣은 STRICT `sql_mode` 확인), 또는 Claude Code 훅(파일 저장 뒤 `ruff` 자동 실행, 작업 끝에 `verify.ps1`) |
| 고치면 | 실패했던 경우를 테스트로 남겨 같은 실수가 다시 통과하지 못하게 함 |

훅·자동 검사 설정은 루트 `.claude/settings.json`에 두고 팀이 같이 씁니다(개인 설정은 `settings.local.json`).

## 2. 서버 구성

### 2-1. Nginx + FastAPI는 어떻게 하나

**클라이언트는 Nginx만 부르고, FastAPI는 밖에서 직접 부를 수 없게 합니다**(정한 것). 강사님 예시(클라이언트가 백엔드를 직접 호출)와 다르게 정한 이유는 아래와 같습니다.

```text
브라우저 ──80──▶ ① Nginx ──/api/* 라운드로빈──▶ ② FastAPI #1 (:8000, public-a)
                  └─ Vue 빌드 정적 파일            ▶ ③ FastAPI #2 (:8000, public-c)
```

| 이유 | 내용 |
| --- | --- |
| 부하 분산을 보여 줌 | FastAPI 2대에 번갈아 보내고, 한 대를 꺼도 다른 대로 넘어가는 시험을 함 |
| 같은 주소 | 화면과 API가 같은 주소라 CORS·쿠키 문제가 없음 |
| 백엔드 숨김 | FastAPI 8000번은 보안 그룹에서 Nginx(sg-web)만 허용, `/api/internal/`·`/api/metrics`는 Nginx가 막음 |
| 한계 | 정문 Nginx가 한 대라 단일 장애점. 조건을 넘으면 ALB로 바꿈(확장안) |

### 2-2. 모니터링은 어떻게 하나

**모든 VM에 Grafana Alloy 하나**를 두고, 서버·서비스별 전용 수집기를 붙여 **모니터링 VM `mon`**(Prometheus·Loki·Grafana, 11-05 로컬 VM)으로 보냅니다(정한 것: 구성 / 제안: 수집기 목록 확정).

| 대상 | 수집기 | 보는 값 |
| --- | --- | --- |
| VM 7대 | node exporter(Alloy 내장 `unix`) | CPU·메모리·디스크·네트워크 |
| FastAPI | 앱 `/metrics`(prometheus_client) | 요청 수·p95·오류율, 예약 결과(`reservation_total{result}`), DB 풀 대기, replica 대체 횟수 |
| MariaDB(`db1`·`db2`) | mysqld exporter(Alloy 내장 `mysql`, 전용 계정 `exporter`) | 연결 수, 느린 쿼리, **복제 지연(`Seconds_Behind_Master`)**, InnoDB 행 잠금 대기 |
| MongoDB | mongodb exporter(Alloy 내장 `mongodb`) | 쓰기 수·지연, 연결 수, 컬렉션 크기 |
| Nginx | `stub_status` + nginx-prometheus-exporter | 활성 연결, 초당 요청, upstream 실패 |
| 로그 | Alloy → Loki | `app.log`(요청·오류), `events.log`(사용자 이벤트), Nginx 접근 로그 |

대시보드는 '서비스(요청·오류·p95)', '예약(성공·409·취소)', 'DB(연결·복제 지연)', '이벤트(수신·저장·대체)' 4장으로 시작합니다.

### 2-3. DB 서버는 어떻게 구성하나

**MariaDB는 Replication(master–slave)**: primary VM `db1`(노트북 1) + replica VM `db2`(노트북 3), GTID 복제(정한 것, 11-05 로컬 VM).

| 항목 | 내용 |
| --- | --- |
| 쓰기 | 모든 쓰기·로그인·'내 것' 조회는 primary |
| 읽기 | 공간 검색·칸·후기 목록 같은 공개 조회만 replica. replica가 안 되면 primary로 대체 |
| 복제 | 비동기. 복제 지연 1초 안팎은 공개 조회에서 허용, 방금 한 예약은 primary에서 읽어 바로 보임 |
| 켜 두기 | replica를 **계속 켜 둠**(로컬 VM이라 비용 없음). 'replica 있음·없음' 비교는 `DB_READ_URL`을 비우고 api 두 대를 다시 시작해서 함 |
| 안 하는 것 | Galera 같은 클러스터(1차 범위 밖). MongoDB는 1대(복제 세트는 확장안) |
| 확인 | Locust로 replica 있음·없음의 조회 p95를 비교해 '읽기 분산 효과'를 숫자로 보여 줌 |

## 4. 자동화 구현

### 4-1. 어떤 사용자를 만드나

**가상 회원 1,000명을 페르소나 4가지로**(제안: 인원 / 정한 것: 유형·비율). 인원은 '사용자 풀 = 하루 방문 × 2.5'(공간 30개 기준 하루 방문 약 420)에서 나옵니다.

| 페르소나 | 인원 | 선호 | 행동 | 포기 조건 |
| --- | --- | --- | --- | --- |
| 대학생 | 350 | 스터디룸·강의실, 평일 오후 | 검색 → 상세 → 칸 선택 → 예약, 이용 후 후기 자주 | 선호 시간대에 빈 칸 없음 |
| 직장인 | 250 | 스터디룸·스튜디오, 평일 19시 이후·주말 오전 | 짧게 검색하고 바로 예약 | 퇴근 시간대가 아님 |
| 모임 | 200 | 파티룸·카페·강의실, 주말 오후, 인원 많음 | 여러 공간 비교, 2~4시간 예약 | 인원·`min_hours`가 안 맞음 |
| 탐색만 | 200 | — | 검색·상세만 보고 나감 | 항상 예약 안 함 |

- 생년월일은 만 14세 이상, 필수 동의 시각은 가입 시각, 모든 행은 `is_synthetic = true`.
- 예약에 실패(409)하면 다른 칸·공간을 1~2번만 더 찾습니다.

### 4-2. 언제 자동으로 실행하나

과거 30일 백필은 11-05 수집 방향입니다. 매일 정해진 시간의 자동 실행은 별도 제안입니다.

| 방식 | 언제 | 무엇 |
| --- | --- | --- |
| 과거 데이터 백필 | 배포 리허설 날 한 번 | 부족한 시연용 공간은 `/internal/venues`로 등록한 뒤, 생성기가 오늘 이전 **30일**의 사용자 행동 데이터를 바로 DB에 씀. 주간 추세가 더 필요할 때만 90일로 확장 |
| 매일 정해진 시간 실행 | 서버를 켜 둔 날(측정·시연 기간) | ②의 cron(Asia/Seoul)이 페르소나별 시간에 Locust를 헤드리스로 돌려 **실제 API로** 이용 |

| 페르소나 | 실행 시간(매일) | 규모 |
| --- | --- | --- |
| 대학생 | 평일 14:00–18:00 | 동시 20명 |
| 직장인 | 평일 19:00–22:00, 주말 10:00–12:00 | 동시 15명 |
| 모임 | 주말 13:00–18:00 | 동시 10명 |
| 탐색만 | 위 시간에 고르게 섞음 | 동시 5명 |
| 같은 칸 몰리기(`SameSlotRush`) | 시연 때 한 번 | 50명이 같은 칸 동시 결제 → 1건만 성공 |

VM을 하루 종일 켜 두지 않으므로(노트북), '매일 특정 시간'은 켜 둔 기간 안에서만 돕니다.

### 5-2. 수집 신뢰성은 어떻게 입증하나

부하 시험과 자동 실행에서 **API를 거친 이벤트만** 세 군데 숫자를 맞춰 봅니다: 보낸 쪽(Locust·프론트) → 서버가 받은 쪽(`events.log` 줄 수) → 저장된 쪽(MongoDB 문서 수). 생성기가 MongoDB에 직접 넣은 과거 이벤트는 이 비교에서 제외하고, 생성기 출력 수와 DB 저장 수를 별도로 대조합니다. 이벤트마다 `event_id`(UUID)가 있어 API 경로의 누락 건을 확인할 수 있습니다.

| 지표 | 계산 | 측정 방법 | 기준(제안) |
| --- | --- | --- | --- |
| 유실률 | 1 − 저장 수 ÷ 보낸 수 | 실행 묶음별로 세 숫자 비교, 빠진 `event_id` 목록 | **0.1% 미만** (대체 저장 뒤 0%) |
| 중복률 | 같은 `event_id`로 저장된 수 ÷ 저장 수 | 같은 `events.log` 문서를 두 번 replay해 MongoDB 문서 수 대조 | **0%** (고유 인덱스가 막음, 건너뛴 건수는 따로 셈) |
| 대체 저장 건수 | MongoDB가 멈춘 동안 `events.log`에만 남은 건수 | 시험 중 MongoDB를 5분 끄고 `replay_events.py`로 다시 넣음 | 다시 넣은 뒤 유실 0, 예약 API 실패 0 |
| 파일 기록 실패 | `event_file_write_failures_total` 증가량 | 부하 전·후 카운터 차이와 `events.log` ID 대조 | **0건**; 잠금은 최대 0.5초 대기 후에도 실패하면 집계 |
| 예약 정합성 | 같은 칸 중복 수, 예약 수 = 결제 수, 칸 수 = 이용 시간 합 | SQL 점검 쿼리 | **중복 0**, 1:1 일치 |
| 동시 결제 | 같은 칸 50명 동시 결제 중 성공 수 | `SameSlotRush` | **정확히 1건** (11-04 로컬 DB에서 2명 동시로 먼저 확인) |
| 서버 | 조회·예약 p95, 오류율(409 제외), 복제 지연 | Locust + Grafana | 동시 50명에서 조회 p95 300ms·예약 p95 500ms·로그인 p95 800ms·오류 1% 미만(5xx·연결 실패·시간 초과, 11-05 A7 확정) |

결과는 `docs/기록/측정_<날짜>.md`에 숫자로 남기고, README '수행결과'에 요약합니다.

이번 #17의 중복률 0%는 **로그 재적재**에만 적용합니다(11-07 PM 결정). 같은 API 요청을 다시 보내는 경우는 별도로 기록하며, 클라이언트 `event_id` 보존과 FE 재시도 계약을 정하는 후속 작업에서 다룹니다.

`events.log` 파일 잠금은 경합 시 최대 0.5초 기다립니다. 이벤트 쓰기 실패는 `event_file_write_failures_total`에 남깁니다. 이벤트 접수 API는 기존처럼 파일 기록 실패 시 503이고, 예약 결과는 파일 기록 실패 때문에 되돌리지 않습니다. 대기 시간 변경이 예약 지연을 키우는지 같은 부하 조건에서 함께 확인합니다.
