## 구현과 검증

전역 RLock 하나를 정규화된 파일 경로별 RLock registry로 변경했다. Registry guard는 잠금 조회/생성 중에만 잡으며 파일 I/O는 파일별 잠금으로 보호한다. 동일 파일의 상대/절대 경로 별칭은 같은 잠금을 사용한다. OS 파일 잠금과 timeout·오류·fallback 계약은 유지한다.

수정 전 app.log를 잡으면 다른 events.log가 timeout 되는 회귀 테스트 실패를 확인했다. 수정 후 Windows 로그/이벤트 pytest21건 및 Ruff 통과. Linux API2의 임시 파일에서 교차파일 독립성·같은파일 배타성·OS 프로세스 배타성·동시64개 JSON 라인 무손상 검증 통과. 기존 Starlette 사용중단 경고1건. DB/프론트 구현은 수정하지 않아 전체 DB/FE suite는 이 검증에서 실행하지 않았다.

API2→API1에 logging.py만 복사하고 restart 후8000/8001 health 확인. 새 SHA256: 2b2b639d23d38f649fb18b33c96b169c532374d8323aa82bdf99cd4e1ca894fc. 이전 파일 및 service/health/Nginx/db.py는 각 VM /var/backups/spacecube/file-lock-split-20261108-01/에 보존. 설정 지문은 배포 전후 동일. Candidate 검증/배포 상세는 이전 실패 run logs/write-high-20261108-185217/의 linux-lock-validation-result.txt 및 deploy-file-lock-api1/api2.txt.

따라서 먼저 파일별 잠금 분리만 비교한다. 동일 파일/OS 잠금 실패가 남으면 lock wait 분포·전체 기록시간·API p95·threadpool 및 큐 점유·유실률을 함께 비교하는 별도0.5초 실험은 타당하다. 현재0.1초 제한에서 잘린 실패 대기만으로0.5초가 충분하다고 확정할 수 없다. 이번에는0.5초 변경을 적용하지 않는다.

### 0.5초 검토에 추가된 근거

파일 분리 뒤에도 동일 파일의 thread timeout2건이 남아0.5초 비교 실험의 근거는 있다. 다만 이번0.1초에서 실패한 스레드가0.5초 안에 성공했을지, 응답p95를 유지할지는 현재자료로 확정할 수 없다. 다음 비교에서는 thread timeout만0.1→0.5로 변경하고 process timeout은0.1을 유지해 한 항목만 바꾸는 편이 원인 분리에 낫다. 그 경우에도 잠금 대기 예산은 최대약0.6초이고 요청지연·동시점유·큐를 함께 판정해야 한다. 이번 사용자 범위에서는0.5초를 적용하지 않았다.
