## 추가 원인 분석

직접 실패는 파일 기록 잠금 경합이다. logging.py의 전역 RLock 하나를 app.log와 events.log가 공유한다. middleware는 모든 HTTP 요청마다 app.log를 동기 threadpool 경로로 기록하고, 예약/취소 이벤트도 같은 append_json을 호출한다. 서로 다른 파일의 쓰기까지 같은 스레드 잠금으로 직렬화된다. 해당 잠금을 가진 상태로 OS 파일 잠금을 기다리고 파일 open/write/close까지 수행하므로, 다른 파일 쓰기에서도 대기열이 길어질 수 있다.

로컬 임시 파일로 현재 _process_lock(app.log)를 잡은 상태에서 append_json(events.log)를 실행하면 thread_lock/lock_timeout이 발생하고, 잠금 해제 뒤에는 정상 기록됨을 재현했다. 결과는 cross-file-lock-reproduction.json. 이는 교차 파일 잠금 결합을 입증한다. 실서버에서 실패 순간 잠금 보유자의 스택·점유 시간을 계측하지 않았으므로, 7건 각각의 보유자가 app.log 요청인지 events.log 요청인지까지는 확정하지 않는다. process_lock 실패1건은 같은 파일에 대한 두 워커 간 경합도 별도로 존재함을 뜻한다.

실패 전60초~abort 뒤15초 DB 관측 최고: primary 연결25/151·실행쿼리3, replica 연결21/151·실행쿼리4. 앱별 행 잠금 대기0·대기시간0·replica 지연0. failure-db-window.json에 보존했다. API RAM은 가까운 표본48%/47%, 디스크 busy도 낮아 이번 자료에서 RAM·용량·지속 디스크 포화를 원인으로 지목할 근거는 없다. CPU 순간78%/67%는 잠금 대기·스케줄링 지연을 악화시켰을 가능성이 있으나 단독 원인으로 확정하지 않는다.

PR97 fallback은 누락8개 이벤트 ID를 Mongo에 저장해 최종 Mongo 유실0을 유지했다. 파일·Alloy·Loki 경로의8개 누락은 여전히 존재하며, 동시간 app.log 기록실패4건도 별도 관측됐다.

다음 수정 검토 우선순위는 로그 기록 경로다. 우선 파일별 잠금을 분리하는 최소 변경을 비교하고, 워커 간 한 파일 쓰기 경합을 줄이려면 단일 writer/유한 큐와 내구성·실패 정책을 함께 설계한다. 0.1초 대기 한도만 늘리는 것은 점유 시간과 지연을 함께 측정한 후 결정한다. DB 연결 한도나 VM 사양을 이번 분석 과정에서 바꾸지 않았다.
