**판정 [사실]**
- 쓰기 200명 예약 p95가 1,022ms에서 81ms로 내려가 500ms 기준을 통과했다.
- 쓰기 400명은 예열·준비·본 측정 모두 HTTP 오류 0으로 처음 통과했다. 3+2 때는 이 단계에서 실패했다.
- 데이터 정합성: 계정 400개 소유 예약·결제 10,468건이 primary·replica 모두 `cancelled/refunded`이고, 합성 표시 10,468/10,468, 남은 시간 칸 0, 복제 IO·SQL Yes·지연 0이다.
- 정리 단계에서 남은 confirmed 예약은 0건이다.
- Uvicorn 동시성 경고 0, HAProxy 상태 전환 0이다(`application-logs.json`).

**해석 [가설]**
- CPU는 두 시험에서 거의 같고, DB 연결은 늘었는데 지연과 오류가 크게 줄었다. 3+2의 200명 지연과 400명 503의 주된 원인이 **앱 풀 획득 대기**였다는 가설을 강하게 지지한다.
- 다만 풀 대기 시간을 직접 잰 것은 아니라 확정은 아니다.
- 실행기도 바뀌었다. Codex가 예열 실패 후 재예약 200이 섞이지 않게 보완했다. 그래서 400명 비교의 일부는 시나리오 차이일 수 있다. 100·200명은 두 시험 모두 오류가 없어 시나리오 차이의 영향이 작다.
- 100명 p95가 62.8ms에서 69.0ms로 약간 늘었다. 한 번씩 측정했고, 데이터도 이전 시험의 예약 이력만큼 늘어나 있었다. 편차 범위인지는 반복 측정이 필요하다.

## 4. 새로 확인한 문제: 이벤트 3건 유실

- [사실] 쓰기 400명 본 측정 끝(22:10:38 KST) api1 `app.log`에 `이벤트 파일 기록 실패`가 3건 남았다. 같은 시각 MongoDB에는 이 시험 계정의 `reservation_complete`가 10,466건, `reservation_cancel_complete`가 10,467건으로, DB 예약 10,468건보다 각각 2건·1건 적다.
- [사실] `mongo_event_write_failures_total`은 0이고, 디스크 여유는 16G, logrotate는 실행되지 않았다.
- [가설·유력] `core/logging.py`의 `_process_lock()`이 프로세스 내부 잠금을 **0.1초**만 기다린 뒤 `OSError`를 낸다. 그러면 `core/events.py`가 그 이벤트를 파일에도 MongoDB에도 보내지 않고 버린다(예약 응답은 정상 유지가 설계 의도). 400명 동시 기록에서 이 잠금 대기가 넘친 것으로 본다.
- 영향: 예약·결제는 정상이고, 분석 이벤트만 약 0.01%가 빠졌다. #17(수집 신뢰성: 유실 측정)의 실측 사례다.
- 제안(A 담당 판단): 잠금 대기 한도 늘리기, 실패한 이벤트를 메모리 큐로 다시 시도, 실패 건수를 지표로 노출.

## 5. 관측 한계

- 풀 획득 대기·스레드 풀 사용량은 계측하지 않았다. 원인 판정은 간접 근거다.
- 읽기 3+2와 읽기 5+5는 배포·데이터·Nginx가 달라 직접 비교할 수 없다.
- 쓰기 3+2 시험 중에는 19:13 대시보드 교체 사고가 있었다(작업판 사고 기록). 이번 쓰기 5+5 시험 중에는 다른 서버 변경이 없었다.
- 쓰기 3+2 이후 Codex가 실행기를 보완했다(예열 실패 격리).
- 각 조건을 한 번씩만 측정했다. 최적값을 확정하지 않는다.
- api1 타이머(`:05` 이용 완료·`:20` 집계)는 끄지 않았다. 21:20·22:05 실행은 본 측정 구간 밖이다.
- Mongo는 exporter가 없어 SSH 1초 표본으로만 봤다. 루트 여유는 2.13GiB로, 시험 전후 변화가 거의 없다.
