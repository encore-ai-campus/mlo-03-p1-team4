# PRO_1 MVP 시뮬레이션·크롤링 수치

2026-10-30 · 노진산

> **11-03 안내:** 예약 단위는 룸이 아니라 공간(`venues`)이고, 날짜는 가상 시계 없이 실제 날짜 + 과거 데이터 백필입니다. 데이터량 추정은 `산출물_04_DB명세서.md` 10절이 기준입니다. 아래 계산 방식(하루 방문 = 하루 칸 수, 사용자 풀 = 하루 방문 × 2.5)은 그대로 씁니다.

MVP는 스터디룸 6개, 하루 84칸(1시간 단위), 가상 사용자 200명으로 가장 가볍게 시작하고, 크롤링으로 주 1개씩 신규 룸을 더해 단계적으로 늘립니다. 모든 수치는 회의에서 확정할 초안입니다.

> **11-01 갱신:** 이 문서는 스터디룸 단독 시절(10-30)의 수치입니다. 그 뒤 5개 유형(스터디룸·스튜디오·카페·영화관·파티룸 → 11-03에 영화관 대신 강의실) 전국 공간대여로 넓혔고(`공간대여_01_기능정의.md`), 일러스트도 10종 × 색 2가지로 늘었습니다. 공간 수·증가폭(시작 10개, 주 +5 또는 +2)은 `회의_2026-11-01_팀원피드백_검토.md` 3-2-4의 제안을 회의에서 정한 뒤 이 문서에 반영합니다. 계산 방식(하루 방문 = 하루 칸 수, 사용자 풀 = 하루 방문 × 2.5)은 그대로 씁니다.

## 단계별 수치

MVP는 4주 동안 룸 6→10개, 하루 84→140칸, 가상 사용자 200→350명 규모로 돌리고, 기준을 통과하면 2단계로 늘립니다.

| 항목 | MVP | 2단계 | 3단계 |
| --- | --- | --- | --- |
| 시뮬레이션 기간 | 4주(28일) | 8주 | 12주 |
| 스터디룸 수 | 6개 시작, 주 +1, 상한 10 | 10 → 20, 주 +2~3 | 20 → 40, 주 +5 |
| 운영시간 | 09:00–23:00 (룸당 14칸) | 동일 | 동일(24시간 룸은 별도 검토) |
| 하루 예약 가능 칸 | 84 → 140 | 140 → 280 | 280 → 560 |
| 하루 방문(세션) | 하루 칸 수와 같게 (84 → 140) | 칸 수 × 1.0 | 칸 수 × 1.2 |
| 가상 사용자 풀 | 200 → 350명 | 350 → 700명 | 700 → 1,400명 |
| 예약 단위 | 1시간 칸, 연속 최대 4칸 | 동일 | 시작·끝 직접 지정(30분 단위) |
| 크롤링 대상 | 스페이스클라우드, 주 1회 | + 쉐어잇 | + 서울시 공공서비스예약 OpenAPI |
| 이미지 풀 | 10종 × 색 2가지 = 20장 (11-01, 5개 유형 포함) | 10종 × 색 4가지 = 40장 | 새 룸 유형 추가 |
| 동시성 부하테스트 | 같은 칸에 동시 50명 | 200명 | 1,000명 + AWS 부하분산 |

## 예약 단위

MVP는 1시간 칸 단위로 예약하고, 시작·끝 직접 지정은 3단계로 미룹니다. 칸 단위면 중복 차단을 DB 유니크 제약 하나로 끝낼 수 있어 동시성 테스트가 단순해집니다.

| 기준 | 1시간 칸 (MVP) | 시작·끝 지정 (3단계) |
| --- | --- | --- |
| 화면 | 칸을 눌러 연속 선택 (설계 화면 그대로) | 시작·종료 시각 선택 |
| 중복 차단 | `(room_id, date, hour)` UNIQUE 한 줄 | 시간 범위 겹침 검사 필요 (`새 시작 < 기존 끝 AND 새 끝 > 기존 시작`) |
| 동시성 | DB가 두 번째 INSERT를 거절 | 잠금이나 배타 제약을 따로 설계 |
| 분석 | 칸 = 점유율 계산 단위와 일치 | 분 단위로 다시 쪼개야 함 |

MVP 예약 규칙:

- 최소 1칸, 최대 연속 4칸(4시간)
- 오늘부터 14일 안만 예약, 이미 지난 칸은 선택 불가
- 저장은 예약 1건 = 예약 테이블 1줄(시작·끝) + 칸 테이블 n줄(칸마다 유니크). 칸 중 하나라도 막히면 전체 롤백

## 예약 가능 칸과 가상 사용자 수

하루 방문 수를 하루 칸 수와 같게 두면 평균 점유율이 약 60%가 되어, 피크 시간만 차고 오전은 비는 현실적인 분포가 나옵니다. 룸이 늘면 같은 규칙으로 사용자도 늘립니다.

1. 하루 칸 = 룸 수 × 14 → 6개면 84칸, 28일이면 2,352칸
2. 목표 평균 점유율 60% → 하루 예약 칸 약 50
3. 예약 1건 평균 2칸 → 하루 예약 약 25건
4. 방문 중 예약 성공 약 30%(탐색만 20%, 조건 불일치 포기 포함) → 하루 방문 약 84 = 하루 칸 수
5. 사용자 1명이 주 2~3회 방문 → 사용자 풀 = 하루 방문 × 2.5 ≈ 200명

MVP 4주 예상 규모(룸 6개 기준, 룸이 늘면 더 많아짐):

| 항목 | 예상치 |
| --- | --- |
| 방문(세션) | 약 2,350 |
| 이벤트 로그 (세션당 5~8개) | 약 1.2만~1.9만 |
| 예약 | 약 700건 |
| 예약 없이 종료 | 약 1,650건 (탐색만 약 470, 포기·중복 차단 약 1,180) |

점유율이 90%를 넘으면 예약봇 상태에 가까워지므로 방문 비율(하루 칸 × 1.0)을 낮추고, 30% 아래면 높입니다.

## 가상 스터디룸 개수와 증가폭

MVP는 설계한 6개(101·102·201·202·301·302)로 시작해 크롤링으로 주 1개씩 더하고, 4주 뒤 10개에서 멈춥니다.

| 주차 | 룸 수 | 하루 칸 | 가상 사용자 풀 |
| --- | --- | --- | --- |
| 1주 | 6 | 84 | 200 |
| 2주 | 7 | 98 | 245 |
| 3주 | 8 | 112 | 280 |
| 4주 | 9 | 126 | 315 |
| 종료 시점 | 10 | 140 | 350 |

- 신규 룸 번호는 층별로 이어 붙입니다(303, 304, 401 …).
- 유형은 크롤링한 공간의 최대 인원으로 정하고, 이미지는 같은 유형의 일러스트를 순환해 붙입니다.
- NEW 배지는 14일 동안 달고, 그동안 해당 룸의 예약 추이를 ‘신규 룸 수요’ 분석에 씁니다.
- 룸을 더하는 날 사용자 풀도 같이 늘려 하루 방문 = 하루 칸 수 규칙을 유지합니다.

## 크롤링 범위

MVP 크롤링은 스페이스클라우드 한 곳에서, 최초 기준선 1회와 주 1회 신규 확인만 합니다. 한 번 돌 때 상세 페이지는 최대 20건만 엽니다.

| 항목 | MVP 값 |
| --- | --- |
| 대상 | 스페이스클라우드 `/space/<id>` |
| 기준선(최초 1회) | 사이트맵 id 목록 저장 + 서울 스터디룸 샘플 30개 상세 수집 → 우리 룸 6개의 가격·인원·시설 값 보정 |
| 주기 | 주 1회 사이트맵을 받아 지난번에 없던 id만 추림 |
| 필터 | 공간유형에 스터디룸 포함 + 최대 인원 10명 이하 + 서울 |
| 등록 개수 | 필터를 통과한 첫 1개만 신규 룸으로 등록(상한 10개까지) |
| 상세 조회 상한 | 회당 20건 |
| 수집 항목 | 공간유형, 수용인원, 시설 아이콘, 시간당 가격, 최소 예약시간, 영업시간 |
| 수집 안 함 | 사진, 후기, 호스트 정보, 연락처, 주소 상세 |
| 요청 간격 | 3초 이상, robots.txt 차단 경로(`/search*`, `/reserve/` 등) 접근 안 함 |
| 저장 | 원본 HTML은 저장하지 않고 추출한 JSON만 + `source_id`, `crawled_at` |

후기·별점 수집은 키워드 분석을 하기로 하면 2단계에서 더합니다.

## 데이터 양 늘리기

MVP 4주치는 예약 약 700건, 이벤트 약 1.4만 건으로 적습니다. 룸 수, 세션당 이벤트 수, 기간이 서로 곱해지므로 이 세 가지를 같이 늘리면 1년에 이벤트 약 2,500만 건이 됩니다.

| 방법 | 무엇을 늘리나 | 배수 | 하루 양 |
| --- | --- | --- | --- |
| MVP 기준 | 룸 6개, 세션당 이벤트 약 6개 | 1 | 이벤트 약 500, 예약 약 25 |
| ① 이벤트 세분화 | 검색 조건 변경, 달력 이동, 칸 선택·해제, 상세 탭 이동, 체류 시간, 예약 취소·변경, 후기 작성, 오류를 모두 기록 → 세션당 약 25개 | ×4 | 이벤트 약 2,100 |
| ② 룸 수 확대 | 크롤링한 스터디룸을 가상 지점으로 계속 추가 (6 → 200개). 사용자는 하루 방문 = 하루 칸 수 규칙대로 같이 늘림 | ×33 | 세션 2,800, 예약 약 840 |
| ③ 기간 백필 | 오프라인 생성기가 가상 시계로 과거 1년치를 빠르게 생성 (28일 → 365일) | ×13 | — |
| ④ 잔여 칸 스냅샷 | 매일 앞으로 14일의 칸 상태를 저장 (200룸 × 14칸 × 14일) | 새 테이블 | 약 3.9만 행 |
| ⑤ 실데이터 수집 | 서울시 공공서비스예약 OpenAPI 일일 스냅샷, 스페이스클라우드 스터디룸 주간 스냅샷(가격·평점·후기 수) | 새 테이블 | 대상 수 측정 필요 |
| ⑥ 인프라 로그 | Locust 부하테스트 중 Nginx·FastAPI 요청 로그 (동시 50명, 평균 3초 간격이면 초당 약 17건) | 부하테스트마다 | 1시간에 약 6만 줄 |

①+②+③을 합치면 2,800세션 × 25개 × 365일 ≈ 이벤트 2,555만 건, 예약 약 30.7만 건입니다.

- **생성 경로를 둘로 나눔:** 대량 데이터는 Locust가 아니라 오프라인 생성기로 만듭니다. Locust는 실제 API를 거치는 부하·동시성 테스트용으로 작게 유지하고, 생성기는 같은 행동 규칙(선호·포기·대안 1~2회)으로 DB나 파일에 바로 씁니다.
- **양보다 실데이터:** ⑤는 양은 작아도 실제 시장 신호라 분석 가치가 가장 큽니다. 가상 데이터는 양을 늘려도 우리가 넣은 규칙만 다시 보여줍니다.
- **저장 공간:** 이벤트 2,500만 건은 한 건 약 300바이트로 잡으면 인덱스 빼고 약 7.7GB입니다. RDS 20GB로는 빠듯하니 50GB로 늘리거나(월 약 $6.6), 이벤트는 날짜별 Parquet 파일(S3)로 빼는 것을 검토합니다.
- **크롤링 범위:** ②를 하려면 MVP 상한(룸 10개, 회당 상세 20건)을 풀어야 합니다. 3초 간격이면 상세 200건에 약 10분입니다.

| 묶음 | 포함 유형 | 전국 (95% 구간) | 서울 | 서울·최대 10명 이하 |
| --- | --- | --- | --- | --- |
| A 학습·회의 | 스터디룸, 회의실, 세미나실, 강의실 | 약 2,050개 (1,460~2,830) | 약 1,550개 | 약 710개 |

- 한 공간이 여러 유형을 함께 달고 있어(예: 회의실·파티룸·스터디룸) 묶음끼리 겹칩니다. 세 묶음을 더하면 전체보다 많습니다.
- 공간유형별로는 파티룸 약 4,670개, 연습실 약 3,750개, 회의실 약 1,270개, 세미나실 약 990개, 강의실 약 780개, 스터디룸 약 640개입니다.
- 지역은 서울 약 59%, 경기 약 18%입니다.
- **권장(10-30 당시):** A 묶음만 엽니다. 예약 방식(시간 단위, 인원, 화이트보드·프로젝터 같은 시설)이 스터디룸과 같아 화면·DB를 그대로 쓸 수 있습니다. B·C는 패키지 요금, 장비, 촬영 조건처럼 예약 규칙이 달라 3단계 이후로 미룹니다.
- **결정(10-30 회의):** 묶음 대신 5개 유형으로 갑니다. 스터디룸(A 묶음), 스튜디오(C의 촬영 계열), 카페·파티룸(B 일부), 영화관(대응 없음). 대응표는 `공간대여_01_기능정의.md` '유형 정의와 크롤링 매핑'. 연습실 계열은 넣지 않습니다.
