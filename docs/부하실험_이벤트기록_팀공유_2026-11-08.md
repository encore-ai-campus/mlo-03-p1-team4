# 부하 실험·이벤트 기록 신뢰성 팀 공유 — 2026-11-08

## 요약

- 11월 7일 쓰기 400명에서 `events.log` 기록 실패 3건, 이후 600명 쓰기 창에서도 append 실패 17건(api1 10·api2 7)이 관측됐다. 예약 응답은 성공했지만 MongoDB 제출 전 파일 기록 경로에서 실패해 이벤트 수 불일치가 발생했다. 잠금 경합은 유력한 가설이지만 당시 로그에 단계·세부 원인이 없어 확정하지 못했다.
- 이벤트 기록의 실패 단계·원인을 계측하고, 예약·취소 서버 이벤트의 MongoDB 대체 전달을 보강했다. 관련 테스트 22건, Ruff, 대시보드 JSON 검증과 PR #97의 DB·백엔드 CI가 통과했다.
- PR #97은 2026-11-08 `36b5895`로 `develop`에 병합됐다. 변경은 아직 VM에 배포되지 않았으므로, 순차 배포·지표 확인·저부하 대사 전에는 새 부하 시험 결과를 만들지 않는다.

## 시스템·측정 조건

시험망은 192.168.219.0/24의 역할별 VM 7대다. 정문 HAProxy `.218`, API `.214`·`.215`, 모니터링 `.217`, MariaDB primary `.212`·replica `.213`, MongoDB `.216`으로 구성한다. 실제 작업은 한 물리 호스트에 VM이 함께 올라가는 경우가 있어 VM별 자원뿐 아니라 호스트 CPU·메모리 경합도 결과에 영향을 줄 수 있다.

관측 경로는 Prometheus가 API/exporter 지표를 pull하고, Alloy가 로그를 Loki로 전달하는 구성이다. 현재 Grafana 문서와 API 대시보드 JSON에 실패 단계·원인 카운터, thread/process 잠금 대기, 전체 파일 기록 시도 시간 패널을 추가했다.

## 이벤트 기록 문제와 변경

### 당시 확인된 사실

- 쓰기 400명 시험 끝 무렵 `이벤트 파일 기록 실패` 3건이 애플리케이션 로그에 남았다.
- MariaDB 예약 수 10,468건에 비해 MongoDB 예약 완료 이벤트는 10,466건, 취소 완료 이벤트는 10,467건이었다.
- MongoDB writer 오류 카운터는 0, 디스크 여유는 약 16GB였고 logrotate 실행도 확인되지 않았다.
- 당시에는 잠금 대기 시간을 분리해 측정하지 않아 0.1초 잠금 timeout이 원인이라는 결론은 가설로만 남았다.

### 보강 범위

- 실패를 직렬화, 디렉터리 준비, thread lock, lock file open, process lock, event file open, append 단계로 구분한다.
- 원인을 lock timeout, permission, disk full, I/O, serialization 등 유한한 코드로 집계한다. OS 예외 메시지·개인정보는 label이나 로그에 넣지 않는다.
- thread/process 잠금 대기 시간과 직렬화부터 파일 기록 시도까지 걸린 전체 시간을 계측한다.
- 예약·취소 서버 이벤트는 파일 기록 실패 시 요청 응답 뒤 MongoDB writer로 전달을 계속 시도한다. 프론트 이벤트 API는 기존 파일 우선 계약에 따라 실패 시 503을 유지한다.
- 0.1초 잠금 대기 제한은 실측 원인을 확인할 때까지 변경하지 않는다.

## 검증 현황

- 로컬 관련 pytest: 22 passed. Ruff lint·format, JSON 파싱, diff 공백 검사를 통과했다.
- PR #97: Ruff·경로 검사·DB/백엔드 통합 CI 통과. 프론트 검사 두 항목은 관련 파일 변경이 없어 건너뛰었다. 현재 리뷰는 대기 중이다.
- 예약 DB 통합 일부는 로컬 `CHECK_DB_URL=spacecube_test` 미설정으로 실행하지 못했다. 운영 DB를 테스트 대상으로 사용하지 않았다.
- VM 재배포, 새 Locust 시험, 실제 Grafana 지표 유입 검증은 아직 하지 않았다.

## 11월 8일 최신 용량·오류 현황

서버 공용 작업판의 `capacity-public-20261108-082946` 결과 기준이다. 이 실행은 예약 쓰기가 아닌 공개 GET 전용이며 7 VM 자원, 40개 Prometheus query, API별 1초 CPU 표본을 기록했다.

|---:|---:|---:|---:|---:|---:|---:|
| 500 | 29,441 | 163.56 | 81.6ms | 33.9% / 34.1% | 81.8% / 82.2% | 0 |
| 600 | 35,129 | 195.16 | 85.4ms | 42.1% / 43.0% | 96.5% / 93.5% | 0 |
| 800 | 46,365 | 257.58 | 227.2ms | 67.2% / 66.5% | 98.5% / 98.0% | 0 |

800 VU는 HTTP·계약 오류와 지연 기준을 통과했지만, API 평균 CPU 50~60% 목표는 넘었다. replica 평균 CPU는 68.5%, 최고 100%, 복제 지연은 0초, 연결 최고는 21개였다. Windows 호스트 RAM 여유는 8GiB 초과, API RAM 최고는 47.6%, Mongo 디스크 여유 최저는 약 2.08GiB로 작업판에 기록됐다. 이는 1초 CPU 표본이며 순간 피크를 완전히 보장하지 않는다.

3 vCPU 증설 시도는 VM의 cores/socket 값이 3을 나누지 못해 api1 부팅 단계에서 실패했고 Locust는 시작하지 않았다. api1을 2 vCPU로 복구한 뒤 7 VM, 두 API health, HAProxy backend와 Prometheus 수집을 확인했다. 현재 하드웨어 변경은 적용 상태가 아니며, 다음 조정 전에 topology를 다시 설계해야 한다.

또한 별도 600명 쓰기 실행에서 Loki가 이벤트 파일 append 실패 17건(api1 10·api2 7)을 보여줬다. 이는 예약 HTTP 성공과 별개인 관측 실패다. 정확한 lock/I/O 원인은 새 stage/reason 지표를 배포하기 전에는 알 수 없다. 서버 작업판의 선행 조건에 따라 저부하 데이터 대사와 새 계측 검증이 끝날 때까지 쓰기 증량은 중단한다.
