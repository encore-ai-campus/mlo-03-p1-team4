# locust — 부하·동시성 테스트 (담당: B 주도, A 지원)

실제 API를 Nginx 너머로 호출해 서버 2대와 DB가 버티는지, 중복 예약이 정말 막히는지 확인합니다.

## 시나리오 (예정)

| 사용자 클래스 | 비중 | 하는 일 | 담당 |
| --- | --- | --- | --- |
| `Browser` | 60% | 메인 → 검색 → 상세 → 칸 조회, 예약 없이 종료 | B |
| `Booker` | 30% | 로그인 → 검색 → 칸 조회 → `POST /reservations`(결제 포함 한 번) (409면 대안 1~2번) | B |
| `Reviewer` | 10% | 로그인 → 후기 모아보기·내 예약 → 후기 쓰기(completed 예약) | A |
| `SameSlotRush` | 별도 실행 | 50명이 같은 공간·같은 칸에 동시에 결제 | B |

- 모든 요청에 `X-Synthetic: 1` 헤더를 붙입니다.
- 대기 시간은 1~5초 무작위 (평균 3초면 동시 50명 ≈ 초당 17건).
- replica 있음·없음(`DB_READ_URL` 비움)을 같은 시나리오로 비교해 p95를 기록합니다(DB 명세 1-2의 '읽기가 많다' 가정 확인).

## 통과 기준

| 단계 | 동시 사용자 | 기준 |
| --- | --- | --- |
| MVP | 50 | `SameSlotRush`에서 201은 정확히 1건, 오류율 1% 미만 |
| 2단계 | 200 | 응답시간 목표(결정 대기, 권장 조회 p95 300ms·예약 p95 500ms), 오류율 1% 미만(409 제외) |
| 3단계 | 1,000 | AWS 부하분산 구성에서 같은 기준 |

## 어디서 돌리나

- MVP·2단계: 내 노트북 → 정문(지금 Nginx, 권장안이면 ALB)
- 3단계(1,000명): 노트북 회선이 먼저 막히므로 같은 VPC에 Locust EC2(예: c7g.large, 시험 동안만)를 띄워 정문으로
- 시험 중에는 `CPUCreditBalance`, RDS 연결 수, 복제 지연, 409 비율을 Grafana·CloudWatch로 같이 봅니다.
- 이 시험 결과가 '나중에 추가'(ALB·Auto Scaling·크기 올리기)를 넣을지 정하는 근거입니다. 잴 것·합격선·추가 조건은 `docs/인프라_트래픽_안정성_검토.md` 1-1절. **서버 1대 끄기 시험**(Locust가 도는 중 FastAPI #2 중지)도 한 번 합니다.

## Playwright와 나누는 일

Locust는 HTTP만 보내 수백~수천 명을 만들고, Playwright는 진짜 브라우저라 한 대에서 수십 명이 한계입니다. 그래서 **트래픽은 Locust**, Playwright는 부하 중에 실제 화면 흐름 2~5명분(검색 → 칸 → 결제 → 후기)을 돌려 화면 지연·오류·프론트 이벤트를 확인합니다. Playwright 요청에도 `extraHTTPHeaders`로 `X-Synthetic`(과 내부 키)을 붙입니다. 근거: `docs/인프라_트래픽_안정성_검토.md` 4절.
